# Tech Blog 記事ネタ棚卸し → 記事化

## この Skill が解決すること

ユーザー（CTO）は日々の Claude Code 作業の中に、社外向け Tech Blog として発信価値のある知見（アンチパターン・設計指針・ケーススタディ・AI活用事例）を持っている。しかしそれはセッション履歴に埋もれており、かつ生データには顧客名・内部数値・非公開仕様など**そのままでは公開できない情報**が混ざっている。

この Skill は次の4段階でそのギャップを埋める。

1. **収集（Collect）** — 対象期間のセッション履歴を棚卸しする
2. **集約 & 公開安全化（Aggregate & Sanitize）** — 横断テーマに束ね、公開可能な粒度へ抽象化する
3. **提案（Propose）** — 記事ネタ候補を一覧で提示し、ユーザーに選ばせる
4. **記事化（Create）** — 選ばれたネタを本リポジトリの規約に沿って記事ファイルに書き出す

**原則: 記事ファイルの作成はユーザーが選択・指示した場合のみ行う。勝手に草案を量産しない**（`AGENTS.md` §8）。迷ったら**公開しない方に倒し、抽象度を上げる**。

グローバル運用ルール（`~/.claude/CLAUDE.md` の「Tech Blogコラムネタの導出手法」）が正であり、本Skillはそれを本リポジトリの規約（`AGENTS.md`・`templates/`）に接続する実装である。

---

## 対象期間の特定

- デフォルトは「呼び出し時点から遡って1週間（7日前の00:00 JST 〜 今）」。
- ユーザーが「先週」「7/1〜7/10」「今月」等を明示したらそれに従う。
- セッション履歴のタイムスタンプは UTC で返る。日本時間（+9h）に変換して期間判定する（UTC 15:00 = JST 翌0:00 の境界に注意）。

## Step 1: 収集（Collect）

1. `mcp__ccd_session_mgmt__list_sessions`（`limit` は対象期間を十分カバーする大きめの値）でセッション一覧を取得する。出力が大きい場合はファイルに落ちるので、Python で期間フィルタ・週次バケットに整形する。
2. **タイトルで読む対象を絞る。** 1週あたり5〜8件。候補者の選考・面談、顧客名が主題のもの、事務作業は最初から除外する。
3. **`mcp__ccd_session_mgmt__list_events` で本文を読む。** アーカイブ済みでもそのまま読める（unarchive は不要）。`limit: 40` から始め、必要なら `before_uuid` で遡る。
   - `search_session_transcripts` は補助に留める。**セッション一覧を抱えたメタセッション（週次レポート等）が検索枠を占有する**ため、`limit` を小さくすると本来の作業セッションが押し出される。20以上にし、メタセッションのヒットは捨てる。
4. **やり取りから暗黙知を吸い出す。** 手順は `AGENTS.md` §5.7 を正とする。拾うのは次の6つ。
   - ユーザーの否定・訂正 → 捨てた案とその理由
   - ユーザーが与えた判断基準 → なぜその手法を選んだか
   - ツール出力の実測値 → 一次観察
   - 方針転換の瞬間 → 記事の山場
   - 保留の宣言 → 「まだ決めていないこと」
   - ユーザーの問い返し → 想定される反論の論点
5. セッションごとに上記を記録する。**タイトルからの推定で済ませない。** 推定でネタを出すと、一次観察が無いまま草案に上がって書き直しになる。

> **実測値も判断の根拠も出てこなかったセッションは、記事にならない**（`AGENTS.md` §5.7.4）。ネタ管理先に留め、材料が揃うまで待つ。

> このリポジトリの `articles/drafts/` と公開済み記事を先に一覧し、**既に執筆済みのネタは重複提案しない**こと。ネタ管理先に起票済みのものはこちらから参照できないため、重複の可能性があるものはユーザーに確認する。

---

## Step 2: 集約 & 公開安全化（Aggregate & Sanitize）

### 集約
個別セッションを横断する**大テーマ**に束ねる（例: RAG/プロンプト設計 / LLMコスト設計 / パフォーマンス / RCA・運用 / エージェント自動化 / エージェント運用そのもの / アーキテクチャ判断）。複数セッションに共通する知見を1つのネタに束ねる。

### 公開安全化 ← 最重要
`AGENTS.md` §5.4「機密情報ガード」を必ず適用する。以下を除去・一般化する。

| NG情報 | 対応 |
|---|---|
| 顧客名・案件名・契約内容・問い合わせ内容 | 削除。「ある顧客案件で」等に一般化 |
| 売上/原価/MRR/ユーザー数などの実額 | 削除。公開情報（公式Pricing等）ベースに再構成 |
| 内部プロンプト文面・内部ファイルパス・リポジトリ名・DBスキーマ | 汎化。再現可能な一般形に言い換え |
| 未公開の脆弱性・障害の生ログ | 抽象化。手法・教訓レベルに落とす |
| 社内URL（Backlog/Stock/Slack等）・社員フルネーム | 削除（GitHubアカウント名は可） |

「固有の事象」→「再現可能な一般的知見（アンチパターン・設計指針・手法）」へ言い換える。**判断がつかない情報は含めない。**

---

## Step 3: 提案（Propose）— 一覧提示とユーザー選択

大テーマ単位で見出しを立て、その下に記事ネタ候補を番号付きで列挙する。各ネタは次を1セットにする。

- **タイトル案**
- **内容**（1〜2行）
- **切り口**（アンチパターン / 設計指針 / ケーススタディ / 比較 のいずれか）
- **想定カテゴリ・タグ**（`AGENTS.md` §6 の体系に合わせる）
- **公開安全性メモ**（抽象化が必要な点があれば一言）

提示フォーマット例:

```
## テーマA: エージェント自動化

1. **タイトル案: ○○○**
   - 内容: ...
   - 切り口: アンチパターン
   - カテゴリ/タグ: ai-agents / AI, MCP
   - 公開安全性: △△を汎化すればOK

2. **タイトル案: ...**
   ...

## テーマB: パフォーマンス
3. ...
```

末尾に**推奨順（優先度）**を添える。優先度は **具体性 × 普遍性 × 意外性 × 公開安全性** で判断する。

そのうえで、必ずユーザーに選択を促す:

> **どのネタを記事にしますか？** 番号で指定してください（複数可）。
> また、`ideas/`（ネタ出しメモ）と `drafts/`（本文まで執筆）のどちらで作成するかも教えてください。

**ここで一旦止まり、ユーザーの選択を待つ。**（AskUserQuestion を使ってもよい。）勝手に次へ進まない。

## Step 4: 記事化（Create）— ファイル生成

ユーザーが選んだネタについてのみ実行する。

### 4-1. 作成先とテンプレート
- ネタ段階を選択 → **リポジトリ外のネタ管理先**（Stock ノート等）へ起票する内容をユーザーに提示する。本リポジトリにはファイルを作らない。
  ネタ管理先は「**いま出さないもの**」の置き場（未着手のネタ／公開留保で解禁待ちの完成草案／取り下げたもの）。
  **一次観察が取れないネタはここに留める。**
  本リポジトリは public なので、この段階のものを持ち込まない（`AGENTS.md` §2）。
  `drafts/` へ昇格させたら、ネタ管理先の該当ネタは消す（昇格は移動であって複製ではない）。
- `drafts/` を選択 → `templates/article_template.md` をベースに `articles/drafts/YYYY-MM-DD_slug.md` を作成（`stage: draft`）。本文は「課題 → アプローチ → 結果 → 学び」の構造で埋める（`AGENTS.md` §5.3）。

### 4-2. 命名・Frontmatter（`AGENTS.md` §3, §4）
- ファイル名: `YYYY-MM-DD_slug.md`（`YYYY-MM-DD` は作成日、`slug` は英数字ケバブケース）。
- Frontmatter は各テンプレート準拠。既定値:
  - `author: "武田 峻一"` / `author_github: "Shunichi-Takeda"`
  - `date` は本日、`stage` は作成先に対応、`category`/`tags` は §6 の体系から選ぶ

### 4-3. 記事の質基準：「仕組み」と「具体」を最優先で書く ← Tech Blog読者が最も求める点
Tech Blog の読者（中〜上級エンジニア）は、抽象的な教訓や「〜が重要です」という一般論では満足しない。**「具体的にどうやっているのか（仕組み）」「実際のコード・手順・落とし穴（具体）」**を知りたがる。公開安全化（§4-2, §5.4）で機密を落とす必要はあるが、**抽象化と“具体を削ること”は別物**である。汎化しつつ具体は残す。

書くときの必達要件:
- [ ] **仕組みを説明する** — 「匿名化しています」ではなく「NERで人名検出→正規化→置換」のように、内部の動作を段階で示す。
- [ ] **実際のコード/コマンド/設定を載せる** — 動く最小例。ライブラリ名・関数・正規表現・`.gitignore`エントリなど具体物を出す（公開OSS名は掲載可）。
- [ ] **ハマりどころ・失敗を書く** — 「これをやらないと動かなかった」という実体験の落とし穴（例: 正規化しないとNERが崩れる）は最も価値が高い。
- [ ] **判断の理由（なぜ）を添える** — なぜその手法を選んだか、代替案との比較。
- [ ] 抽象的な提言だけで終わっていないか、**「読者が自分の環境で再現できるか」**で自己点検する。

> 迷ったら「これは “What” だけで “How” が抜けていないか？」を問う。抜けていれば、機密に触れない範囲で仕組み・具体を足す。元セッションだけで具体が足りなければ、参照先のリポジトリ・コードまで確認して実装の実体を掴む。

### 4-3b. 見出し・強調・反論（実運用で最も手戻りした3点）

**1) テンプレートの見出しをそのまま使わない**

`templates/article_template.md` は構成の指示書であって見出しの雛形ではない。
`## はじめに` `## 背景・課題` `## アプローチ` `## 結果` `## 学び・今後の展望` を残した記事は、
**過去4本すべてが書き直しになった**（`ai:GeneralPreamble` と `ai:RecapOnlySummary` を構造として抱えるため）。

```
×  ## はじめに          →  ○  ## 「本当に戻るのか」に答えられなかった
×  ## 背景・課題        →  ○  ## なぜ0件になるのか
×  ## 学び・今後の展望  →  ○  ## まだ決めていないこと
```

**2) 本文の太字は主張2箇所まで**（`ai:TableOveruse`）

過去に163箇所使われていて、全記事で1桁超過していた。太字が20箇所あると、どれが主張か読者に分からない。
表のセルと段落先頭の連番ラベル（`**1. 事前告知**`）は構造表示なので対象外。まとめ節の箇条書きで再強調しない。

**3) 主張の強い記事には「想定される反論」を立てる** ← 最も落ちやすい

次のいずれかに当てはまるなら、この節が**必須**（`voice:CounterArgument` = `required: conditional`）。

- 読者が反対の立場を取れる主張が本文にある
- 一般に推奨されている方法を採らなかった
- コストや安全性のトレードオフを引き受けた

**回答はAIが書かない。** 判断の中身は著者しか持っておらず、書くと必ず一般論になる（`AGENTS.md` §8-8）。
やるのは次まで。

```
1. 反論の論点を3〜4つ立てる（読者の立場で、記事の主張に正面から当たるもの）
2. 各論点について「答えるために何の材料が要るか」を添える
3. ユーザーに提示して材料をもらう
4. もらった材料を文章に落とす（「」で反論を引用し、認めるところから入る）
```

既存記事11本のうち**8本でこの節が欠けていた**。口語では相手が反論してくれるので自分で立てる必要がなく、
文章に移したときにだけ必要になる特性（`voice:ElicitingQuestion`）。意識しないと必ず落ちる。

**4) Zennの制約**

- **HTMLコメントを本文に書かない** — Zenn は HTML を解釈しないため、読者にそのまま表示される
- レビュー用のメモは草案側に置く（変換時に `draft_to_zenn.py` が除去する）
- `topics` は5件まで、slug は `a-z0-9` とハイフン・アンダースコアの12〜50文字

### 4-4. 品質・機密チェック（コミット前に必ず）
`AGENTS.md` §5.3 必須要件と §5.4 機密情報ガードを再チェックする。特に:
- [ ] Stock社固有の機密情報（顧客名・内部数値・非公開仕様・社内URL）を含まない
- [ ] 外部エンジニアにとって再現可能な形になっている
- [ ] タイトルが具体的で得られる知見が明確
- [ ] §4-3 の「仕組み・具体」要件を満たしている

### 4-5. Zenn 公開への引き継ぎ
`drafts/` に草案を作った場合、その先の公開フローは [PUBLISHING.md](../../../PUBLISHING.md) を正とする。**ユーザーの指示があった場合のみ** `python3 scripts/draft_to_zenn.py <草案>` で `articles/<slug>.md`（`published: false`）に変換し、`python3 scripts/validate_zenn.py` でエラー0を確認する。**`published: true` への変更・merge は行わない**（`AGENTS.md` §8-6）。

> ⚠️ **本リポジトリは public である。** ネタの段階（書くと決めていない、公開留保がかかっている、取り下げた）のものを `articles/drafts/` に置いてはならない。それらはリポジトリ外のネタ管理先で管理する（`AGENTS.md` §2）。**本リポジトリに `articles/ideas/` は作らない。**

### 4-6. 完了報告
作成したファイルパスと、各ファイルの1行サマリを提示する。
**コミット・公開はユーザーの指示があるまで行わない**（`AGENTS.md` §8: 公開判断は必ずCTOが行う）。コミットしてよいか一言確認する。

## やってはいけないこと

- ユーザーが選ぶ前に記事ファイルを作る。
- **セッションのタイトルや検索snippetからの推定でネタを出す**（`AGENTS.md` §5.7.2）。`list_events` で本文を読む。推定で出したネタは一次観察が無く、草案に上げると書き直しになる。
- 機密情報ガードを飛ばして生データのまま記事化する。
- **公開安全化を口実に、仕組み・具体まで削って抽象論だけの記事にする**（§4-3 違反）。汎化と「具体を消すこと」は別。
- テンプレートの見出しをそのまま残す（＝書き直しになる）。
- 想定される反論への「回答」を自分で書く（論点を立てて著者に問い返すまでが範囲）。
- 一次観察が取れないネタを `drafts/` に上げる（ネタ管理先に留める）。
- 経営層向け業務報告（weekly/daily-report）と混同して、社外公開に不適な内部詳細を書く。
- 公開可否をAI側で判断する／勝手にコミット・push・公開する。
- `published: true` に書き換える、または main に merge する（＝Zennへの公開そのもの）。
