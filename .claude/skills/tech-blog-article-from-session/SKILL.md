# 指定セッション → Tech Blog 記事化

## この Skill が解決すること

[[tech-blog-idea-digest]] が「1週間分を横断して記事ネタを棚卸しする」のに対し、本Skillは**対象セッションが既に決まっている**ケースを扱う。「あの調査を記事にしたい」という具体的な起点があるとき、そのセッションを深掘りし、公開安全化した上で**1本の記事（draft または idea）に仕上げる**。

グローバル運用ルール（`~/.claude/CLAUDE.md` の「Tech Blogコラムネタの導出手法」）と本リポジトリの規約（`AGENTS.md`・`templates/`）に従う。**記事の作成・コミット・公開はユーザーの指示があった場合のみ**行う（`AGENTS.md` §8）。

---

## Step 1: 対象セッションの特定

ユーザーは次のいずれかの形で対象を指定する。特定して確定させる。

- **セッションのタイトル/トピックで**（例:「AI検索ラリーの調査」）→ `mcp__ccd_session_mgmt__list_sessions` / `mcp__ccd_session_mgmt__search_session_transcripts` で該当を探す。
- **session_id で** → `mcp__ccd_session_mgmt__get_session` でメタ情報を取得。
- **「今のこの作業」「さっきの作業」** → 現在の会話文脈が対象。必要なら関連セッションを補足検索。

複数候補がヒットして曖昧なときは、候補を提示して**どれか確認する**（AskUserQuestion 可）。複数セッションを1記事に束ねる指定もありうる。

---

## Step 2: 深掘り（Deep-dive）← 本Skillの肝

一覧化Skillと違い、ここでは**記事に足る密度まで technical core を掘る**。表面のタイトルやsnippetで満足しない。

1. `mcp__ccd_session_mgmt__search_session_transcripts` を、そのセッション由来の**技術用語・エラー文・関数名・ライブラリ名**で複数回叩き、原因・対策・使った仕組みを拾う。
2. **セッションが参照している実物まで辿る** — 対象がコード/設定/スクリプトに触れているなら、そのリポジトリ・ファイルを実際に開いて**実装の実体（関数・正規表現・コマンド・`.gitignore` 等）を確認する**。記事の「具体・仕組み」はここから出る。
3. 次を言語化してメモ化する:
   - **課題**（何が問題だったか）
   - **仕組み/アプローチ**（どう解決したか＝内部動作を段階で）
   - **具体物**（実際のコード・コマンド・設定・落とし穴）
   - **なぜ**（その手法を選んだ理由・代替案）
   - **結果・学び**

---

## Step 3: 公開安全化（Sanitize）

`AGENTS.md` §5.4「機密情報ガード」を必ず適用する（[[tech-blog-idea-digest]] と同一基準）。

- 顧客名・案件名・実額・社内URL・社員フルネーム・内部リポジトリ名・チケット番号・製品固有名を除去/汎化。
- 内部プロンプト文面・DBスキーマ・生ログは一般形に言い換える。

> **重要**: 公開安全化は「機密を落とす」ことであって「具体・仕組みを削る」ことではない。**汎化しつつ具体は残す**（Step 4 の質基準）。判断がつかない機密は含めない。

---

## Step 4: 切り口とアウトラインの提示 → ユーザー確認

いきなり全文を書かず、まず**切り口とアウトライン**を提示して合意を取る。

- **切り口**（アンチパターン / 設計指針 / ケーススタディ / 比較）
- **タイトル案**（1〜3案）
- **アウトライン**（見出し構成：課題 → アプローチ → 結果 → 学び）
- **想定カテゴリ・タグ**（`AGENTS.md` §6）
- **`ideas/` と `drafts/` のどちらで作るか**（未指定なら確認）

ここで一旦止まり、ユーザーの合意・修正を待つ。（既に「draftで」等が明示されていれば省略して進めてよい。）

---

## Step 5: 記事化（Create）

合意した内容で記事ファイルを作成する。

### 5-1. 作成先とテンプレート
- ネタ段階（まだ書くと決めていない）→ **リポジトリ外のネタ管理先**（Stock ノート等）に起票する。本リポジトリには置かない。ファイルとして残す必要がある場合は、ユーザーに内容を提示して移送を委ねる。
- `drafts/` → `templates/article_template.md` ベース、`articles/drafts/YYYY-MM-DD_slug.md`（`stage: draft`）。本文は「課題 → アプローチ → 結果 → 学び」で埋める。

### 5-2. 命名・Frontmatter（`AGENTS.md` §3, §4）
- ファイル名 `YYYY-MM-DD_slug.md`（`YYYY-MM-DD` は作成日、`slug` は英数字ケバブケース）。
- `author: "武田 峻一"` / `author_github: "Shunichi-Takeda"` / `date` は本日 / `category`・`tags` は §6 / `source_context` は公開安全化済みの表現で。

### 5-3. 記事の質基準：「仕組み」と「具体」を最優先で書く ← Tech Blog読者が最も求める点
Tech Blog の読者（中〜上級エンジニア）は、抽象論では満足しない。**「具体的にどうやっているのか（仕組み）」「実際のコード・手順・落とし穴（具体）」**を求める。必達要件:
- [ ] **仕組みを段階で説明する**（「〜しています」で終わらせず、内部の動作を分解して示す）。
- [ ] **実際のコード/コマンド/設定を載せる**（動く最小例。ライブラリ名・関数・正規表現・設定エントリ等の具体物。公開OSS名は掲載可）。
- [ ] **ハマりどころ・失敗を書く**（「これをやらないと動かなかった」は最も価値が高い）。
- [ ] **判断の理由（なぜ）と代替案** を添える。
- [ ] 「読者が自分の環境で再現できるか」で自己点検する。

> 自己点検の問い: 「これは “What” だけで “How” が抜けていないか？」。抜けていれば Step 2 に戻り、機密に触れない範囲で仕組み・具体を足す（必要なら参照先コードを再確認）。

### 5-3b. 見出し・強調・反論（実運用で最も手戻りした3点）

**1) テンプレートの見出しをそのまま使わない**

`templates/article_template.md` は構成の指示書であって見出しの雛形ではない。
`## はじめに` `## 背景・課題` `## アプローチ` `## 結果` `## 学び・今後の展望` を残した記事は、
**過去4本すべてが書き直しになった**（`ai:GeneralPreamble` と `ai:RecapOnlySummary` を構造として抱えるため）。

```
×  ## はじめに          →  ○  ## 「本当に戻るのか」に答えられなかった
×  ## 背景・課題        →  ○  ## なぜ0件になるのか
×  ## 学び・今後の展望  →  ○  ## まだ決めていないこと
```

**2) 本文の太字は主張2箇所まで**（`ai:TableOveruse`）

過去に163箇所使われていて、全記事で1桁超過していた。太字が20箇所あると、どれが主張か読者に分からない。
表のセルと段落先頭の連番ラベル（`**1. 事前告知**`）は構造表示なので対象外。まとめ節の箇条書きで再強調しない。

**3) 主張の強い記事には「想定される反論」を立てる** ← 最も落ちやすい

次のいずれかに当てはまるなら、この節が**必須**（`voice:CounterArgument` = `required: conditional`）。

- 読者が反対の立場を取れる主張が本文にある
- 一般に推奨されている方法を採らなかった
- コストや安全性のトレードオフを引き受けた

**回答はAIが書かない。** 判断の中身は著者しか持っておらず、書くと必ず一般論になる（`AGENTS.md` §8-8）。
やるのは次まで。

```
1. 反論の論点を3〜4つ立てる（読者の立場で、記事の主張に正面から当たるもの）
2. 各論点について「答えるために何の材料が要るか」を添える
3. ユーザーに提示して材料をもらう
4. もらった材料を文章に落とす（「」で反論を引用し、認めるところから入る）
```

既存記事11本のうち**8本でこの節が欠けていた**。口語では相手が反論してくれるので自分で立てる必要がなく、
文章に移したときにだけ必要になる特性（`voice:ElicitingQuestion`）。意識しないと必ず落ちる。

**4) Zennの制約**

- **HTMLコメントを本文に書かない** — Zenn は HTML を解釈しないため、読者にそのまま表示される
- レビュー用のメモは草案側に置く（変換時に `draft_to_zenn.py` が除去する）
- `topics` は5件まで、slug は `a-z0-9` とハイフン・アンダースコアの12〜50文字

### 5-4. 品質・機密チェック（コミット前に必ず）
`AGENTS.md` §5.3 / §5.4 を再チェック:
- [ ] Stock社固有の機密情報（顧客名・内部数値・非公開仕様・社内URL・実名・内部リポジトリ名）を含まない
- [ ] 外部エンジニアにとって再現可能
- [ ] §5-3 の「仕組み・具体」要件を満たす

### 5-5. Zenn 公開への引き継ぎ
草案が書き上がったら、公開フローは [PUBLISHING.md](../../../PUBLISHING.md) を正とする。**ユーザーの指示があった場合のみ**、変換まで進める。

```bash
python3 scripts/draft_to_zenn.py articles/drafts/<草案>.md   # → articles/<slug>.md（published: false）
python3 scripts/validate_zenn.py                             # エラー0を確認
```

> ⚠️ **本リポジトリは public である。** 草案を `articles/drafts/` に置いた時点で、Draft PR であっても誰でも読める。書くと決めていないネタ・公開留保がかかったもの・取り下げたものは、リポジトリ外のネタ管理先で別管理する（`AGENTS.md` §2）。

- 変換で `topics` が5件超になると切り詰め警告が出る。落とす対象が妥当か確認し、必要なら `--topics` で明示する。
- 未マップのタグは警告に出る。`config/zenn.json` の `tag_to_topic` に追加する。
- **`published: true` への変更・merge は絶対に行わない**（レビュー承認後に人が実施。`AGENTS.md` §8-6）。

### 5-6. 完了報告
作成ファイルパスと1行サマリを提示。**コミット・公開はユーザー指示があるまで行わない**。コミットしてよいか一言確認する。

---

## やってはいけないこと

- 深掘り（Step 2）を飛ばし、snippet だけで薄い記事を書く。
- 参照先コードを確認できるのに確認せず、仕組み・具体を想像で埋める（＝事実に基づかない記述）。
- 公開安全化を口実に具体・仕組みまで削り、抽象論だけの記事にする。
- テンプレートの見出しをそのまま残す（＝書き直しになる）。
- 想定される反論への「回答」を自分で書く（論点を立てて著者に問い返すまでが範囲）。
- 本文に HTML コメントを書く（Zennで読者に表示される）。
- 機密情報ガードを飛ばす／公開可否をAI側で判断する／勝手にコミット・push・公開する。
- `published: true` に書き換える、または main に merge する（＝Zennへの公開そのもの）。
