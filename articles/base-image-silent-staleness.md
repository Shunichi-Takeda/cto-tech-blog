ベースイメージのOSがサポート切れになり、ビルドが止まる。これは痛いですが、壊れることで「更新しろ」と教えてくれています。

危ないのは逆側です。ビルドが通り続けるイメージは、誰にも気づかれないまま何年も本番で動き続けます。

棚卸しの軸を、ビルドの成否からベースイメージの最終更新日に移しました。コンテナを本番で動かしているなら、10分で一覧が出せる話です。

## 止血のあとに残った問い

きっかけは、あるサービスのイメージビルドが突然落ちたことでした。ベースイメージのOSがサポート期間を終え、パッケージの取得元がビルド中に使えなくなったためです。

止血はすぐ済みました。取得元の指定を調整して、ビルドを通るようにしただけです。

一段落したところで、私から問い返しました。「古いOSのままでいるのは、リスクとして高くないか」。

答えは「高い。ただし、危険の順序が直感と逆」でした。

## 危険度を並べたら、1位は「ビルドが止まったもの」ではなかった

本番で動いているイメージを1つずつ調べ、危険度の順に並べ直しました。

| 順位 | 状態 | 気づける経路 |
|---|---|---|
| 1 | 本番のイメージのベースが、何年も前のビルドのまま。TLSを担うライブラリも、上流のサポートが切れたブランチのまま焼き込まれている | なし。ビルドは通り、サービスも正常に動く |
| 2 | ビルド中にOSのパッケージを取得しないサービスが、サポート切れのランタイムで本番稼働している | なし。取得しないので、取得元が消えてもビルドが落ちない |
| 3 | 次にビルドしたとき、また取得元の問題でビルドが止まる | ビルドの失敗として必ず見える |

直感では3位が一番目立ちます。実際に止まったのはこれで、課題も起票されていました。

1位と2位は、どちらも課題がありませんでした。

**起票されているものとされていないものの差は、危険度の差ではなく、ビルドが落ちたかどうかの差でした。**

2位は特に象徴的です。Dockerfile にOSのパッケージを取得する行が無いサービスは、取得元が消えても何も起きません。調べた時点で、ランタイムのサポートが切れてから年単位が過ぎていましたが、ビルドは通り続け、サービスも普通に動いていました。

3位は、深さの方は浅いと分かりました。サポートが切れたOSのパッケージは、アーカイブ用の配布元に残っています。参照先を差し替えるだけで復旧できることを確かめました。最初は「2度目の緊急対応が確定する」と見積もっていたのですが、これは言い過ぎでした。リリース直前に踏むと痛い、というのが正確なところです。

## 止血が、もう1つ「静かな側」を増やしていた

並べ直して気づいたことがもう1つあります。ビルドを通すための止血で、セキュリティ更新の取得元を外していました。

ビルドは通るようになりました。そのかわり、その時点から、OSのセキュリティ更新は二度と入りません。止血したことで、1位と同じ「静かに古くなる」状態をもう1つ作っていたことになります。

止血そのものは、その日のリリースを通すために必要でした。ただ、止血の差分が何を捨てたかは、恒久対応の課題に書いておかないと消えます。

## 最近ビルドしていても、中身は古いことがある

もう1つの落とし穴は、「最近ビルドしたイメージなら新しい」という思い込みです。

アプリのイメージは毎週のようにビルドし直していました。レジストリ上の push 日時は新しい。ところが、`FROM` でベースイメージのタグを固定していると、ベースの中身はそのタグが最後にビルドされた時点のままです。上流がそのタグの更新をやめていれば、何回ビルドしても古いOSのライブラリが入り続けます。

見るべき日付は2つあります。

```bash
# 1) アプリのイメージを最後に push した日時（ECR）
aws ecr describe-images --repository-name my-app \
  --query 'sort_by(imageDetails,&imagePushedAt)[-1].[imagePushedAt,imageTags[0]]' \
  --output text

# 2) そのイメージの FROM に書いたベースイメージが、上流で最後にビルドされた日時
docker pull -q my-base:1.2.3 >/dev/null
docker image inspect -f '{{.Created}}' my-base:1.2.3
```

1つ目が新しくても、2つ目が古ければ中身は古いままです。棚卸しで見るのは2つ目です。

リポジトリをまたいで一覧にするなら、Dockerfile の `FROM` を集めて、ベースイメージの作成日時の古い順に並べます。

```bash
# 作業ディレクトリに各サービスのリポジトリを並べておく前提
grep -h '^FROM' */Dockerfile* \
| awk '{print $2}' | grep -v '^\$' | sort -u \
| while read -r img; do
    docker pull -q "$img" >/dev/null 2>&1 || { echo "pull-failed $img"; continue; }
    printf '%s %s\n' "$(docker image inspect -f '{{.Created}}' "$img")" "$img"
  done \
| sort
```

`FROM ${BASE}` のように変数を使っている行は拾えないので、別に確認します。マルチステージビルドでは、最後のステージのベースが本番で動くものです。

この一覧と、本番で実際に動いているサービスを突き合わせます。稼働しているかどうかは、リポジトリの最終コミット日では判断できません。コミットが長く止まっているので休眠中と判定したサービスが、実際には本番で動いていた、ということがこの調査の中でもありました。稼働状況はオーケストレーター側（ECSならサービスの起動数）で確かめます。

## 何を選んで、何を捨てたか

最初に考えたのは「全部を一気に最新に上げる」でしたが、これは採りませんでした。OS、言語ランタイム、フレームワーク、データベースは互いに依存しています。言語の新しいメジャー版が今のフレームワークの版では動かない、という組み合わせもありました。開発の予定と並行して進めるには、段階に分けるしかありません。

次に考えたのは「ビルドが落ちたものから順に直す」です。普通はこうなります。今回の発見はまさに、この順序だと1位と2位が最後まで残る、ということでした。

採ったのは、次の順序です。

- 本番で動いていて、ベースが古いものを先にする（ビルドの成否は問わない）
- 同じ検証で済むものはまとめる。たとえばTLSライブラリのメジャー更新と、署名検証を使うライブラリの更新は、同じ回帰テストを通すので1つの検証にする
- 使っていないパッケージは、更新する前に消す。コードから一度も呼ばれていないパッケージを入れていて、それが脆弱なライブラリを引き込んでいた。消せば、脆弱性ごとイメージから消える

3つ目は工数がほぼゼロで、効果が一番はっきりしていました。更新は検証が要りますが、削除は「使っていない」ことを確かめるだけで済みます。

## 想定される反論

「ベースイメージの更新は、自動で更新PRを出すツールに任せれば済むのでは」

同じ系列の中の更新なら、ツールで回せます。届かないのは、系列そのものが終わったときです。

ベースイメージのタグを固定していると、上流がその系列のビルドをやめた時点で、ツールが提案できる新しい版がなくなります。次の系列に移るには、言語ランタイムやフレームワークとの組み合わせを確かめる必要があり、それは更新PRの自動マージでは済みません。

もう1つ、ツールは本番で何が動いているかを知りません。休眠中に見えて実は動いていたサービスのように、どこを優先するかの判断は、稼働状況と突き合わせないと出てきません。

「壊れているものから直すのは、優先順位として合理的ではないか」

止血の順番としては合理的です。ビルドが止まると開発が止まるので、その日のうちに止血しました。

ただ、止血の順番と、恒久対応の順番は別です。止血は、落ちたものから。恒久対応は、危ないものから。ビルドが落ちたものは、落ちた時点で誰かが必ず手を付けます。何年も未パッチのまま静かに動いているものは、順番を意識して上げないと、最後まで誰も手を付けません。

一気にすべてを上げるのは、工数と工期の面で難しい状況でした。だから、どれから上げるかの順番の方が重要でした。

「ベースが古くても、脆弱性スキャンで問題が出ていなければ十分ではないか」

スキャンは、既に知られている脆弱性を数えるものです。数えられるのは、見つかった分だけです。

サポートの切れたOSには、新しく見つかった脆弱性の修正がもう出ません。スキャンが何かを見つけたときに、直す手段が残っていないことになります。最終更新日が見ているのは、脆弱性の有無ではなく、まだ直せる状態にあるかどうかです。

スキャンは別の課題として進めています。どちらか一方ではなく、両方の軸で見ます。

「止血でセキュリティ更新の取得元を外したのは、そもそも悪手ではないか」

外さなければ、その日のリリースが止まっていました。

それに、外した取得元は、既にサポートが終わっていました。外したから更新が来なくなったのではなく、もう新しい更新は来ない状態でした。外して失ったのは、更新そのものではありません。「更新が来ていない」とビルドの失敗で知らせてくれる警報の方です。

だから止血のあと、外したことを恒久対応の課題に書き、脆弱性対応の親課題の下に段階的な更新を並べました。警報を止めたなら、代わりに覚えておく場所が要ります。

## まだ決めていないこと

棚卸しをどの頻度で回すかは、まだ決めていません。月に1回なら手でも回せますが、ベースイメージの作成日時が一定の日数を超えたら知らせる、という形で仕組みにするかを迷っています。閾値をいくつにするかの根拠がまだ無いためです。

段階的な更新の順序も、開発の予定と並べて組み直している途中です。順序は決めましたが、どの段をいつ入れるかは、ほかのリリースとの兼ね合いで動きます。

## まとめ

- ビルドが落ちるイメージは、壊れることで更新を知らせてくれる。落ちないイメージは、誰にも気づかれずに古くなる
- 課題の有無は危険度ではなく、ビルドが落ちたかどうかで決まっていた
- アプリのイメージを最近ビルドしていても、固定したベースイメージの中身は古いままのことがある。見るのはベースイメージの作成日時
- 稼働しているかはコミット日ではなく、本番の起動数で確かめる
- 更新の前に、使っていないパッケージを消す。脆弱性ごと消える
