メンバーの稼働時間帯がそろわず、全員が同時にオンラインになる時間帯がほとんどない。デイリーの朝会は物理的に設けられません。かといって「毎朝チャットで報告してください」と求めるのも、開発時間を報告という雑務に変えることになります。

PMは把握したいが聞くのも申し訳ない。メンバーは報連相の重要性を理解しているが、目の前のコードに集中したい。お互いに遠慮しながら中途半端、という状態が続いていました。

## 「報告」に本当に新しい作業が必要なのか

ここで立ち止まりました。メンバーは日々、すでに多くの痕跡を残しています。

- 課題管理ツールでタスクのステータスを更新している
- 情報共有ツールに個人メモとして日次の作業内容を書いている
- GitHubにコミットし、PRを出している

これらを集約・分析するだけで、「いま誰が何をしていて、どのくらい進んでいるか」は相当の精度で把握できるはずです。

**メンバーに新しい作業をさせるのではなく、既にやっていることから吸い上げる。** これがコンセプトでした。

## 3つのデータソース

```
[課題管理ツール]   [情報共有ツール]   [GitHub]
  (計画データ)       (活動データ)     (客観データ)
      │                  │              │
      └──────────────────┴──────────────┘
                         ▼
          AIエージェント（LLM + MCP）
       収集 → 突合・進捗判定 → レポート生成
```

人間が新たに入力する情報はゼロです。

### 1. 課題管理ツール — 「何をやるべきか」

Web APIで各メンバーの進行中課題を取得します。使うフィールドは3つ。

| フィールド | 用途 |
|---|---|
| 期日 | 当初計画の基準日 |
| マイルストーン | 現在のリリース計画（常に最新化されている） |
| 見積り工数 | 消化率の算出 |

期日とマイルストーンの差分が、スケジュールスリップを検出する鍵になります。

### 2. 情報共有ツール — 「昨日何をしたか」

メンバーが自分用に書いている作業メモを読みます。ここで意識したのは、本文（ストック情報）は取得しないことです。日次のメッセージだけを対象にする。

これは技術的な制約ではなく設計判断でした。個人的なメモの詳細まで覗ける仕組みにすると、書く側が萎縮します。「見られている」と感じさせないことが、痕跡の質を保つ条件です。

### 3. GitHub — 「コードが正」

口頭の進捗報告より、PRの状態が真実を語ります。PRを7段階に自動分類しました。

| ステージ | 判定条件 |
|---|---|
| マージ済み | `state=MERGED` |
| 承認済み | `reviewDecision=APPROVED` かつ Open |
| レビュー中 | レビューコメントあり かつ Open |
| レビュー待ち | Open かつ レビュアー未割当 |
| 開発中 | Open かつ 7日以内に更新あり |
| 停滞 | Open かつ 7日以上更新なし |
| PR未作成 | 課題は進行中だがPRなし |

## 効くのは「乖離の検出」

このステージ分類で見えるようになったのは、単体の進捗ではなくデータソース間の食い違いでした。検出できる乖離は3種類あります。

- **課題は進行中なのに、PRもブランチも存在しない** — 未着手か、ローカルで抱えたままpushされていない
- **APPROVEDなのにマージされていない** — リリース調整か、依存関係か、単に忘れられているか
- **レビュー待ちのまま更新が止まっている** — レビュアーの割当漏れ

どれも1つのツールだけを見ていては気づけません。ステータスを見るだけなら「進行中」ですし、GitHubを見るだけなら「PRがない」だけです。**突合して初めて異常になる。**

そしてこれらは、週次の定例で「なんか止まってるPRない？」と聞くまで見つからない種類の問題でした。デイリーで自動検出されるようになったことが、いちばん大きな変化です。

## 判定ルールで学んだこと

最初は期日を超過したら即「遅延」と判定していました。実運用してみると、ノイズだらけになります。

- 期日は当初計画であり、**変更されないことが多い**
- マイルストーンは常に最新化され、**実際のリリース計画を反映**している
- マイルストーンが期日より後ろにズレるのは「スリップ」だが、**関係者と合意済み**であることが多い

そこで判定を組み替えました。

```
🔴 遅延（要対応）  : マイルストーンの期日を超過している
🟡 注意（参考情報）: マイルストーン > 期日 だが、マイルストーン期日内
🟢 オンスケ        : マイルストーン期日内
```

スリップ = 即遅延ではない。 これをルール化したことでノイズが減り、本当に対応が必要な課題だけが浮かび上がるようになりました。アラートは、鳴りすぎると見られなくなります。

## 仕様をコードとして管理する

この仕組みで最も効いたのは、レポートの仕様自体をリポジトリに置いたことです。`AGENTS.md` にデータ収集手順、7段階の判定ロジック、テンプレート、判定ルールを全部書きました。

これにより、セッションが変わってもエージェントが変わっても同じ品質のレポートが再現される。判定ロジックの変更もGitの差分として追跡できます。

もうひとつ徹底したのは読み取り専用であることです。収集は全てGETと読み取り専用の経路のみ。エージェントが誤ってデータを更新・削除するリスクを、アーキテクチャのレベルで排除しました。

## 想定される反論

「痕跡からは量しか分からず、質的な進捗は見えないのでは」

見えません。ただ、日報に求めているのはそこまでです。誰がどのタスクを抱えていて、どれが止まっているか。中身がどこまで進んでいるかは、別のトラッキングで見る話だと切り分けています。

日報で全部を把握しようとすると、結局メンバーに書かせることになります。それが最初に外したかったものでした。

「これは監視ではないのか」

隠して集めているものはありません。タスクもマスタースケジュールも課題管理ツールで管理していて、メンバー自身が見られる場所にあります。この仕組みがやっているのは、そこに既にある情報を突き合わせて並べ直すことです。

「AIの進捗判定が誤ったら、PMが誤った判断をするのでは」

誤ります。ただ、それは人が書いた日報でも同じです。書かれた内容を100%鵜呑みにしてマネジメントして、良い結果が出ることはありません。

レポートは判断材料の1つです。実態を掴む手段はほかにもあります。1on1、定例、普段の仕事ぶり。どれか1つに全部を預けないというだけの話だと思っています。

「3つのツールに依存していて、どれかが変わったら壊れるのでは」

壊れたら直します。APIが通らなくなれば、そのデータソースは人が見に行って、内容をAIに伝えればいい。

これはAIに限った話ではありません。想定どおりに動かない状況が生まれたときに、どう解消するかを考えて動けるかどうかです。壊れない仕組みを作ることより、壊れたときに手で戻せる状態にしておくほうを優先しています。

## まだ手をつけていないこと

レポートをメンバー本人にも共有し、セルフマネジメントに使ってもらう案があります。ただ迷っています。

この仕組みは乖離を検出するものなので、本人に渡すと監視として受け取られる可能性があります。そうなると、痕跡を「良く見せるため」に操作するインセンティブが生まれる。データの信頼性が落ちれば、仕組み自体が意味を失います。

渡し方の設計ができていないので、まだ止めています。

## まとめ

- メンバーに報告という追加作業を課さないのが最も重要な設計判断。既存ツールの痕跡だけで組む。
- 効くのは単体の進捗ではなく、データソース間の乖離の検出。突合して初めて異常になる。
- PRの状態を7段階に分類し、「コードが正」の原則で客観的に判断する。
- スリップ ≠ 遅延。判定ルールを実運用で組み替えないと、アラートはノイズになる。
- 仕様は `AGENTS.md` にコード化する。収集経路は読み取り専用に固定する。
- 覗ける範囲を意図的に狭める。見られていると感じさせないことが、データの質を保つ。
