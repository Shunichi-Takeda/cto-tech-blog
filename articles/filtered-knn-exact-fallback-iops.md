テナントごとのフィルタを付けたベクトル検索は、条件によっては近似検索をやめて、総当たりに切り替わります。

総当たりは、クライアントがタイムアウトして接続を切っても止まりません。そこへ再試行を重ねると、同じ全件読み込みが何本も並んで走ります。ディスクが飽和し、関係のないキーワード検索まで巻き添えで落ちました。

厄介なのは、そのあいだCPU使用率が2%前後で、1分平均のIOPSにも何も出ないことです。OpenSearch で k-NN を使っているなら、この記事のコマンド2つで自己診断できます。

## CPUは2%、それでも検索が止まった

始まりは、ALB の `HTTPCode_Target_5XX_Count` が1分間だけ跳ねたアラートでした。ALB 自体の5XXはほぼ0件で、トラフィックも平常どおり。ECS のタスクも全部 healthy でした。

アプリのログを見ると、エラーはすべて OpenSearch への検索の `Faraday::TimeoutError` で、処理時間は3.0〜3.5秒にそろっていました。クライアント側の3秒のタイムアウトです。しかも特定のテナントではなく、複数のテナントで同時に起きていました。

OpenSearch 側では、検索スレッドのキューが平常時の0から198まで積み上がり、そのノードの検索処理（`SearchRate`）は1分あたり約480件から9件までほぼ止まっていました。

一方で `CPUUtilization` は平均1〜5%。最初の見立ては「セグメントのマージか、GCの停止だろう」でした。CPUが低くてキューだけ跳ねるなら、何かのI/O処理が一時的に割り込んだと考えたからです。

確かめたら、どれも0でした。GCの停止も、force merge も、シャードの移動もありません。代わりに出てきたのが次の2つです。

```bash
# 1分平均の ReadIOPS と、秒単位の最大値（MicroBursting）を並べる
for m in ReadIOPS ReadIOPSMicroBursting CPUWait; do
  aws cloudwatch get-metric-statistics --namespace AWS/ES \
    --metric-name "$m" \
    --dimensions Name=DomainName,Value=my-domain Name=NodeId,Value="$NODE_ID" Name=ClientId,Value=123456789012 \
    --start-time 2026-09-28T02:30:00Z --end-time 2026-09-28T02:50:00Z \
    --period 60 --statistics Average Maximum \
    --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Average,Maximum]' --output text
done
```

`CPUWait` は事象の時間帯に77〜94%でした（平常時は1〜10%）。**CPUが低かったのは余裕があったからではありません。**ディスクの読み込みを待って、何もできずに止まっていたのです。

`ReadIOPS` の1分平均は数十〜200程度にしか見えませんでした。ところが秒単位の `ReadIOPSMicroBursting` は、事象の外でも日中は3,300〜4,400で、gp3 の既定の上限3,000 IOPSに張り付いていました。

以前の調査メモには「EBSの読み込みは日中でも上限の1割」と書いていました。1分平均を見て書いたもので、誤りです。

## 遅いのは「冷えたテナントの1回目」だけだった

ディスクを何がそんなに読んでいるのか。並行して追っていた「大規模なテナントのベクトル検索だけ遅い」件と、ここでつながりました。

同じテナントに同じ検索を2回投げると、こうなります。

| テナントの規模 | 1回目 | 2回目 |
|---|---|---|
| 大 | 23.5秒 | 47ms |
| 中 | 8.6秒 | 49ms |

1回目だけが数秒〜数十秒かかり、2回目は数十msです。シャードのコピーが3つある場合は、コピーごとに1回ずつ「1回目」を踏みます（18.6秒 → 15.5秒 → 37ms）。1回目の時間は、k や ef_search を変えてもほとんど動かず、テナントの件数にほぼ比例していました（1件あたり約0.1ms）。

ディスク側を見ると、1回の読み込みは約4KB、読み込みのレイテンシは約1ms、キューの深さは1〜1.5でした。ベクトルを1件ずつ順番に読んでいて、上限ではなくレイテンシで律速されている形です。

## なぜ総当たりに落ちるのか

OpenSearch 2.x の k-NN プラグイン（faiss エンジン）は、フィルタ付きの検索をまず近似検索（HNSW のグラフ探索）で処理します。このとき、フィルタに合う結果が k 件そろわなかったセグメントは、フィルタに合う全件を総当たり（exact search）で計算し直します。

HNSW の探索は、おおよそ `max(ef_search, k)` 個のノードを訪ねたところで打ち切られます。フィルタに合う結果は、そのうち「テナントの選択率 × 訪問数」くらいしか拾えません。

```
セグメント全体: 100万件
テナントの選択率: 2%
ef_search（既定）: 100、k: 500
  → 訪問できるのは約500件、そのうちフィルタに合うのは約10件
  → k=500 に届かない → このセグメントは総当たりへ
```

選択率が数%のテナントで k=500 を取りにいくと、ほぼ必ず総当たりに落ちます。総当たりはグラフを使わず、Lucene 側に保存された元のベクトル（fp32、1件4KB）をディスクから読みます。グラフがメモリに載っていても関係ありません。

2回目が速いのは、読んだベクトルがOSのページキャッシュに残っているからです。ここで言う「冷えている」は、ページキャッシュから追い出された状態のことです。

## タイムアウトしても、サーバーは読み続ける

ここで一つ、前提が崩れました。

調査の途中まで、「クライアントが3秒でタイムアウトすれば、サーバー側の検索も止まる」という説明を受け入れていました。止まるなら、「総当たりを短いタイムアウトで試し、間に合わなければ近似の結果を返す」という手が使えます。

本番で確かめました。冷えた大規模テナントに、目印のヘッダーを付けた総当たりを2秒のタイムアウトで投げ、直後から `_tasks` を1秒ごとに見ます。

```bash
# 検索に目印を付けて投げる（2秒でタイムアウトさせる）
curl -s -m 2 -H 'X-Opaque-Id: cancel-test' -H 'Content-Type: application/json' \
  "$OS/my-index/_search" -d @query.json

# 目印の付いたタスクが残っているかを見る
curl -s "$OS/_tasks?actions=*search*&detailed=true" \
| jq '[.nodes[].tasks[] | select(.headers["X-Opaque-Id"]=="cancel-test")
       | {action, cancelled, sec: (.running_time_in_nanos/1e9)}]'
```

結果はこうでした。

- タイムアウト直後に、親タスクとシャードごとの検索の計5件に `cancelled: true` が付いた
- しかし開始から32秒たっても、5件とも動き続けていた
- 同じ検索をすぐ投げ直すと、2回目は133秒かかった（止まらない1回目とディスクを取り合った）
- 夜間で他の負荷がほとんど無いのに、1ノードの `CPUWait` が61〜67%のまま3分続いた

**キャンセルの印は付くのに、総当たりの読み込みは止まらない。** これで「短いタイムアウトで試す」案は消えました。

同時に、障害を広げていた仕組みも見えました。アプリは3秒で打ち切って最大6回再試行していたので、冷えたテナントへの検索1件につき、止まらない全件読み込みが最大6本並んでいたことになります。さらにアプリ側には、増幅する要因が3つありました。

- scroll 検索にタイムアウト時の後片付けが無く、OpenSearch 側に300件近い scroll が残っていた
- 全文検索を4並列で投げていた
- ジョブが10秒後に全体を再実行しており、混雑の4分間に48回走っていた

1つ目は `ensure` で `clear_scroll` を呼ぶだけで直ります。

```ruby
# opensearch-ruby 3.x
def scroll_all(client, body)
  res = client.search(index: "my-index", scroll: "1m", body: body)
  scroll_id = res["_scroll_id"]
  hits = res["hits"]["hits"]
  while (page = client.scroll(body: { scroll_id: scroll_id }, scroll: "1m"))["hits"]["hits"].any?
    scroll_id = page["_scroll_id"]
    hits.concat(page["hits"]["hits"])
  end
  hits
ensure
  client.clear_scroll(body: { scroll_id: scroll_id }) if scroll_id
end
```

## 私の案は、どれも効かなかった

並行して、インフラ側でも手を打っていました。結果から言うと、私が出した案はどれも効いていません。

| 案 | 狙い | 結果 |
|---|---|---|
| EBS の IOPS を3倍にする | 読み込みの上限を上げる | 1回目の時間は変わらず。総当たりは順番読みでレイテンシ律速のため、上限まで届いていなかった。元に戻した |
| ディスクを増やして1セグメントに統合する | 小さいセグメントの検索コストを減らす | 2セグメントへの統合で改善はほぼ出切り、1セグメント化の上乗せは測れなかった。総当たりの経路には効かない |
| スループットの増加、データノードの追加 | 読み込みを分散する | 総当たりはテナントのデータを持つシャード単位で走るため、上限を上げても1本の順番読みは速くならない |

IOPSを3倍にしたのは、私の判断です。上限に張り付いているなら上限を上げればいい、と考えました。効かなかった理由は前の節のとおりで、張り付かせていたのは「多数の検索の合計」であって、1本の総当たりはそもそも上限まで使えていません。

## ef_search で避けられる。ただし精度と引き換え

総当たりを避ける最短の手は、クエリで探索幅を広げることでした。k-NN のクエリには `method_parameters` で `ef_search` を渡せます。

```json
POST /my-index/_search
{
  "size": 500,
  "query": {
    "knn": {
      "embedding": {
        "vector": [0.012, -0.031, ...],
        "k": 500,
        "method_parameters": { "ef_search": 3000 },
        "filter": { "term": { "tenant_id": 42 } }
      }
    }
  }
}
```

冷えた大規模テナントで、本番の設定（ef_search は既定）だと108秒かかった検索が、`ef_search: 3000` を足すと0.04秒で返りました。

代わりに精度が落ちます。総当たりの上位30件を正解として測ると、一致率は大規模テナントで0.97から0.89、別のテナントで0.95から0.78に下がりました。実際の検索語20件で比べると、最終的に使う上位の結果が、半分の検索で入れ替わりました。ef_search を足した方が良くなった検索は1件もありません。

そこで、一律には足さず、「件数が多く、利用が少なくて冷えやすいテナント」だけに限りました。冷えていなければ総当たりでも速く、足すと精度が下がるだけだからです。

ところが1週間後、ef_search=3000 を足した大規模テナントで、また55秒の検索が出ました。同じクエリを ef_search=10000 で投げても55秒です。一部のセグメントは、探索幅をいくら広げても k 件そろわない形をしているようでした。「ef_search を上げれば避けられる」という案は、ここで撤回しています。

## 暖機の評価は3回ひっくり返った

総当たりを避けきれないなら、ページキャッシュを温めておけばいい。この「暖機」の評価は、3回ひっくり返りました。

1回目。夜間に暖機すると、温まった状態が20分〜2時間もちました。これなら定期実行で足りると考えました。ところが日中に同じことをすると、30分もちません。日中は他のテナントの検索や全文検索がひっきりなしにディスクを読むので、暖機で載せた領域が押し出されます。競合相手は暖機対象のテナント同士ではなく、インデックス全体への業務アクセスでした。

2回目。その後、ページキャッシュに使えるメモリが大きい機種に替えました。午前に間隔を変えて測ると、温まった状態は少なくとも30分続きました。15分おきなら足りる、という見立てです。ところが午後、利用が戻った時間帯には、暖機から13〜15分で冷えるテナントが出ました。

3回目。15分おきの暖機を実際に回すと、暖機対象のテナントで3秒を超える検索は午前の4分の1になり、タイムアウトは0件になりました。13時半以降は、冷えた検索がありません。

暖機の対象の選び方も途中で変えています。最初は「検索件数の多い上位のテナント」を選んでいました。それに対して出た判断基準が「自力で温めるのが難しいテナントこそ対象にすべき」です。

理屈はこうです。3秒で打ち切られた検索も、サーバー側では読み込みを進めます。利用者の再試行1回ごとに、テナントのデータが一定量ずつ温まっていく。ということは、再試行の上限まで重ねても読み切れない件数を持つテナントは、どれだけ使われても温まりません。そういうテナントは件数の割に利用が少ないことが多く、検索件数で選ぶと必ず漏れます。対象は件数で選ぶように直しました。暖機の検索にも `X-Opaque-Id` で目印を付け、スローログで利用者の検索と分けて数えています。

## 想定される反論

「タイムアウトを延ばせば済む話ではないか」

延ばしました。ただ、延ばしても総当たりそのものは速くなりません。3秒で打ち切って再試行を重ねるより、1本を最後まで待つ方が、ディスクに積まれる読み込みが少なくて済む、という判断です。あわせて再試行の回数と間隔も調整しています。

「1分粒度の監視で十分ではないか。秒単位まで見るのは過剰では」

平常時の傾向を見るなら、1分粒度で足ります。足りないのは「上限に張り付いているか」を判定するときです。

1分平均は、張り付いている数秒と空いている残りの時間を均してしまいます。実際、私は1分平均を見て「読み込みは上限の1割」と書きました。秒単位で見たら、日中ずっと上限に張り付いていました。

秒単位の指標をアラームにはしていません。その代わり、CPUが低いのに検索が詰まったときは、最初に `CPUWait` と秒単位のIOPSを見ることにしています。

「精度を落としてまで速くするのは、検索として本末転倒ではないか」

一律に落としたわけではありません。ef_search を足したのは、件数が多く、利用が少なくて冷えやすいテナントだけです。冷えていないテナントは、総当たりでも速く返るので、精度を落とす理由がありません。

対象のテナントについては、比べたのは「少し違う結果」と「結果が返らないこと」です。3秒で打ち切られる検索は、利用者から見れば答えが無いのと同じです。少し質が下がっても、返る方を選びました。

ただ、この手は1週間後に撤回しています。探索幅をいくら広げても総当たりに落ちるセグメントがあったためです。いまの対策の中心は暖機です。

「暖機は場当たりのハックで、根本対策ではないのでは」

根本対策ではありません。つなぎです。

根本は、総当たりに落ちない形にすることで、候補は「まだ決めていないこと」に書いた2つです。バージョンを上げて切り替えを抑えるか、大規模なテナントを別のインデックスに分けるか。どちらも戻しにくい変更なので、効くと確かめる前には入れません。

その間を埋めるのが暖機です。費用はごく小さく、要らなくなればスケジュールを止めるだけで戻せます。戻せる手で時間を稼ぎ、戻せない手は測ってから入れる、という順番にしています。

## まだ決めていないこと

OpenSearch 3.x には、フィルタ付き検索の精度を上げる機能や、総当たりへの切り替えを止める設定があります。ただ、メジャーバージョンの更新は戻せません。総当たりを止める設定は精度が大きく落ち、精度を上げる機能はメモリ最適化の構成が前提です。戻せない変更を、効くかどうか分からないまま入れる段階ではないと考えて、検証環境で測ってから決めることにしています。

大規模なテナントだけを別のインデックスに分ける案もあります。フィルタが無くなれば、総当たりへの切り替えそのものが起きません。そのかわり、検索の振り分けとデータ移行の仕組みが要ります。

暖機の15分という間隔も、データが増えたときにもつかは分かっていません。冷えた検索の件数をスローログで毎日数え、増えてきたら見直すつもりです。

## まとめ

- フィルタ付きのk-NN検索は、近似で k 件そろわないセグメントを総当たりで計算し直す。選択率が数%のテナントで大きな k を取ると、ほぼ必ず落ちる
- 総当たりは、クライアントがタイムアウトしてもサーバー側で止まらない。`cancelled: true` が付いても読み続ける。再試行は全件読み込みを並列に積み上げる
- CPU使用率が低いのは、余っているからとは限らない。`CPUWait` と、秒単位の `ReadIOPSMicroBursting` を見る
- IOPSの上限を上げても、順番読みの総当たりは速くならない
- ef_search を足すと総当たりを避けられるが、精度と引き換えで、セグメントの形によっては効かない
- 暖機の対象は検索件数ではなく、自力で温まれない件数かどうかで選ぶ
