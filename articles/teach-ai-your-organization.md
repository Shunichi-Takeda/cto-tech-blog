AIに開発を任せたときの出力の確かさを決めるのは、モデルの賢さではありませんでした。AIがその組織をどれだけ知っているか、そして工程のどこまでを通しで見せているか、の2つです。

**AIが外すのは、組織の事情を知らない場所です。** そして欠陥が見つかるのは、工程と工程の継ぎ目です。

![AIだけでは無難な案しか出ず、組織のナレッジを読ませて変える流れと、工程のブロック1つだけでなく継ぎ目を見る、という見どころのドット絵](/images/teach-ai-your-organization/overview.png)

## 無難な案に落ち着く

以前、プライベートでコードを書いていたときのことです。AIにコードを生成させると、いつも無難な案に落ち着きました。間違ってはいません。ただ、自分が実現したかったことは、結局叶いませんでした。

いま振り返ると、理由は単純でした。AIは、その場で渡された文脈しか知りません。文脈が無ければ、どこでも通用する一般解を返すしかない。無難な案は、AIなりの誠実さの結果です。

Stock社に来てからは、この「文脈」の側を育て続けています。リポジトリを横断して使う組織のナレッジを1つのリポジトリにまとめ、AIエージェントが作業のたびに参照する形です。始めてから約5か月で、更新は240回を超えました。

## 入口は「参照タイミング」の表

ナレッジのリポジトリのルートに置いた説明ファイルには、次の形の表があります。エージェントは作業を始めるとき、まずここを読みます。

| ナレッジ | ファイル | 参照タイミング |
|---|---|---|
| 詳細設計 作成ガイド | `design/creation_guide.md` | 詳細設計書を新規作成するとき／テストコンディションを作るとき |
| PRレビューチェックリスト | `code-review/pr_review_checklist.md` | PR のレビューを行うとき |
| アラーム調査ワークフロー | `operations/alarm_investigation.md` | 通知チャンネルでアラームが鳴ったとき |
| 教訓カタログ（症状索引） | `lessons/README.md` | 原因が分からないとき／2回直しても進まないとき／「直った」と報告する前 |
| 個人設定 | `users/<アカウント名>.md` | 個人固有の環境情報を参照・更新するとき |

効いているのは3列目です。

AIは「どのファイルに何が書いてあるか」を聞かれれば探せます。ただ、作業の最中に「いまこれを開くべきだ」とは気づきません。そこで参照の条件を、話題ではなく状況で書きます。「アラームについて」ではなく「アラームが鳴ったとき」。「教訓」ではなく「2回直しても進まないとき」です。

リポジトリ固有のルールは、各プロダクトのリポジトリに置いた説明ファイルに書きます。横断のナレッジとは分けています。同じことを両方に書くと、片方だけが古くなるためです。

## AIが外した場所が、そのまま規約になる

ナレッジの大半は、最初から書いたものではありません。AIが外したあとに足したものです。代表的なものを3つ挙げます。

1つ目。課題管理ツールの課題に「メール通知」とだけ書かれていた案件がありました。AIはコードから該当する通知を探しましたが、見つかりません。正体は、依頼書の本文にある1文からしか分かりませんでした。依頼書は情報共有ツールのノートで、課題には要約しか転記されていなかったのです。以後、依頼書の本文は必ず取得することを既定にしました。

2つ目。ある施策は複数のフェーズに分かれていて、AIは依頼されたフェーズだけを設計しました。実際には前のフェーズが別の課題として既にあり、依頼されたフェーズはそのデータを読む前提でした。施策全体をまとめた親ノートに、それが書いてありました。以後、依頼書から親ノートへのリンクがあれば、先に親を読むことにしています。

3つ目。依頼書にメッセージで要件の変更が届いていたのに、AIは古い理解のまま設計を進めました。依頼書の更新日時と設計の日付を比べる規約は、既にありました。ところが、メッセージが付いてもノートの更新日時は変わりません。外部APIで実測して確かめています。規約を守っていても、すり抜ける形でした。いまは、メッセージの作成日時も比べます。

どれも、モデルの能力では防げない外し方です。この組織では仕様の正本がどこにあり、どう書き換わるのか。その癖を知らないことが原因でした。

### 否定の知識が、個人のメモに閉じていた

10月に、エージェントの個人メモリと組織のナレッジを突き合わせました。個人メモリ177件のうち45件が、棄却した仮説や効かなかった対策でした。一方、組織のナレッジの側で「不採用」「仮説」と書かれた箇所は、それぞれ2件しかありませんでした。

「こうすれば動く」はナレッジに上がっていました。上がっていなかったのは「こう考えたが違った」の方です。次に同じ症状を見た人やエージェントが最初に疑うべきことは、むしろこちらに書いてあります。

そこで、症状から引く教訓のカタログを新しく作りました。参照タイミングの表の「2回直しても進まないとき」の行が、それです。

## 工程の一点ではなく、通しで見せる

もう1つの柱が、工程を横断させることです。

AIの使い方として多いのは、コーディングだけ、レビューだけ、という一点での使い方だと思います。それでも各工程の質は上がります。ただ、その場合に見えない欠陥があります。設計と実装の食い違い、テストの書き方と本番の入口の食い違いのように、工程と工程の間にある欠陥です。

いまは、1つの案件を次の流れで通します。

```
依頼書（情報共有ツールのノート）
  └→ 課題（課題管理ツール）          … 案件の正本。工数・期日
      └→ 詳細設計（GitHub Issue）    … 設計の正本
          ├→ テストコンディション（スプレッドシート）… 手動テストの正本
          └→ Draft PR                               … 実装の正本
              └→ 全成果物のクロスチェック（別のエージェント）
                  └→ STG テストと証跡
```

成果物は4つの場所に散ります。互いを参照し合うので、どれか1つだけ直すと、残りと静かに矛盾します。この流れの中心にあるのは、その整合を保つことです。

### クロスチェックは別のエージェントに、全成果物を横断させる

作成したエージェントとは別のエージェントに、全成果物をまとめて読ませます。観点は8つです。要件と設計、設計と実装、ユースケースと自動テストとテストコンディション、テストコンディション単体、課題の記載、相互リンクの陳腐化、実装の品質、他の PR との関係。

ある案件での推移は次のとおりです。

| 回 | must | should | nit | 所要 |
|---|---|---|---|---|
| 1回目 | 3 | 8 | 10 | 約16分 |
| 2回目 | 1（課題本文の更新が人の承認待ち） | 3 | 3 | 約6分 |
| 3回目 | 1（同上） | 0 | — | 約4分 |

2回目の should 3件は、どれも1回目の指摘を直した結果、新しく生まれたものでした。

その1つは、こうです。1回目の指摘への修正として、取り残された状態を後から戻すための処理が足されました。ところがその処理は、承認されて既に公開済みになったものまで戻してしまう作りでした。直した PR が、別の不具合を持ち込みかけたわけです。2回目のクロスチェックがそれを止めました。

### 横断して初めて見つかった欠陥の型

1回目の must のうち2件は、どちらか一方の工程だけを見ていたら見つからないものでした。

1件目は、要件と、別の機能の相互作用です。要件には「元に戻すときは通知を一切出さない」とありました。実装は、戻すときにレコードを更新します。すると更新日時が進み、更新日時を見て毎時まとめ通知を送る既存のバッチの対象に入ります。戻した1時間後に、全メンバーへ通知が届く形でした。

2件目は、テストの入口です。

```ruby
# PR に含まれていた spec（形を汎用化）
# 内部のメソッドを直接呼んでいるので、本番の入口を通っていない
it "フォルダ削除で申請が消えた場合も、元の状態に戻す" do
  Folder.delete_approval_requests(folder.id)
  expect(item.reload).to be_visible
end
```

本番の入口（フォルダ削除の API）では、申請を消す処理は非同期ジョブに積まれます。その前に、同じリクエストの中で下書きが同期で消え、申請も一緒に消えます。ジョブが動く時点では申請が0件で、元に戻す処理は空振りします。spec は内部のメソッドを直接呼んでいたので、この順序を通りませんでした。

いまは、PR レビューのチェックリストに「本番と同じ入口から確かめているか」を入れています。spec はジョブの実行を含めて、API に対するリクエストとして書きます。

```ruby
it "フォルダを削除すると、承認待ちだったものが元に戻る" do
  perform_enqueued_jobs do
    delete "/api/v1/folders/#{folder.id}", headers: auth_headers
  end
  expect(item.reload).to be_visible
end
```

コードのレビューは設計の要件を見ません。設計のレビューは、テストがどの入口を通るかを見ません。**継ぎ目は、両方を同時に読む人がいないと見えない。**工程を横断させる意味は、ここにあります。

別の時期に29件をまとめて処理したときも、作成したエージェント自身のセルフチェックを通った成果物で、23単位中18単位に must が出ました。テストが実行できない、性能が大きく落ちる、PR どうしが衝突する、といった中身です。どれも、作った側の視点からは見えていませんでした。

## 聞かずに進める範囲を決める

工程を通しで回すと、エージェントからの確認が増えます。過去の実運用で、選択肢を示して聞いたものを振り返ると、ほぼすべてが「推奨どおり」で返っていました。

そこで、推奨どおりで確定しているものは既定として書き、聞かずに進めることにしました。クロスチェックの指摘も、コメントで残して人が直すのではなく、その場で成果物に反映して再チェックに回します。

逆に、聞くものも決めています。課題の本文の全文を書き換える更新は、元に戻しにくい操作なので、差分を見せて承認を取ります。本番の DB に対する読み取り以外の操作も同じです。境界は、後で戻せるかどうかで引いています。

## 捨てた案

| 案 | 採らなかった理由 |
|---|---|
| コーディングだけ、レビューだけをAIに任せる | 工程の継ぎ目にある欠陥が見えない |
| クロスチェックの指摘をコメントで残し、人が直す | 往復のたびに人の手が要り、指摘が溜まる。直した結果を再チェックする工程も抜けやすい |
| 組織のルールを各プロダクトのリポジトリにすべて書く | 横断のルールが複数の場所に分かれ、片方だけが古くなる |

## 想定される反論

「ナレッジの保守コストが高くつくのでは。古くなった規約は、無いより害になる」

保守コストはかかります。古い規約が害になるのも、そのとおりです。実際に、撤去した経路の手順がナレッジに残ったままで、別の手順と矛盾していたことがありました。

だから、古さに気づく役もエージェントに持たせています。作業の途中でナレッジと実態の食い違いに気づいたら、その場で直す変更を出させ、人がそれを確かめてから取り込みます。ナレッジを使うのも、古さに最初に気づくのもエージェントなので、気づいた場所で直すのがいちばん安くつきます。

更新は約5か月で240回を超えました。多く見えますが、1回の大半は数行の修正です。

「書き手がほぼ一人なら、属人化の置き場所を移しただけでは」

書き手が偏っているのは事実です。更新の大半は私です。

ただ、属人化で困るのは、本人がいないと誰も判断できなくなることです。ナレッジに書いた時点で、判断の根拠は私の頭の外に出ています。そして、読み手は人ではなくエージェントです。メンバーが自分のエージェントで作業しても、同じナレッジを参照する設定にしています。

書き手を増やす方は、各自の環境で業務を通じて出てきたナレッジを、そのまま共有のリポジトリに上げることを奨励しています。

「同じモデルどうしのクロスチェックは、自己確認にすぎないのでは」

同じモデルでも、渡す文脈が違えば、見えるものが違います。作った側は自分の意図を知っているので、成果物を意図どおりに読みます。クロスチェックをする側には、成果物だけを渡します。

実際、作った側のセルフチェックを通った成果物でも、23単位中18単位で must が出ました。直したPRが別の不具合を持ち込みかけたのを止めたのも、2回目のクロスチェックです。

自己確認で済むとは考えていないので、人のレビューとSTGテストは残しています。クロスチェックが何を取りこぼしたかは、まだ数えられていません。これは「まだ決めていないこと」に書いたとおりです。

「推奨どおりなら聞かない、という既定は、人の判断を空洞化させないか」

聞いても推奨どおりに返していた確認は、判断ではなく、確認の作業になっていました。それを減らしたのが、この既定です。

人の判断が要るのは、後で戻せないところです。課題本文の全文の書き換えや、本番DBへの読み取り以外の操作は、いまも必ず聞かせています。

人の役割は、作業の一つひとつに承認を出すことから、「何をやるか」と「何をもって良しとするか」を決めることに移していくつもりです。

## まだ決めていないこと

どの知識を組織のナレッジに上げ、どれを個人のメモに留めるか。いまは「別の案件でも、次に疑うことが変わる知識」なら上げる、という線で運用しています。ただ、この線で十分かはまだ判断できていません。個人メモリの側にも、上限を超えて末尾が読み込まれていない、という別の問題が残っています。

クロスチェックが取りこぼしたものを数える方法も、まだ決めていません。後工程で見つかった不具合を、クロスチェックの観点に照らして分類する必要があります。その記録の取り方がまだ無い、というのが正直なところです。

後編では、この流れの最後の工程である STG テストの環境を、課題ごとに作って消す形にした話を書きます。

## まとめ

- AIが無難な案に落ち着くのは、渡された文脈しか知らないから。組織の文脈を渡す手立てがあるかどうかで、出力の確かさが変わる。
- ナレッジの一覧は、話題ではなく「いつ開くか」の状況で書く。
- 規約の多くは、AIが外した場所から生まれる。棄却した仮説や効かなかった対策も、組織の側に上げる。
- コーディングやレビューの一点ではなく、工程を通しで見せる。欠陥は工程の継ぎ目にある。
- 聞かずに進める範囲と、必ず聞く範囲を、後で戻せるかどうかで分ける。
