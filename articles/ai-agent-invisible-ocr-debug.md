OCR処理済みのPDFで、検索ハイライトが実際のテキストと全く違う場所に出る。ところがPDFの見た目は完全に正常で、原因が掴めない。AIエージェントに調査を任せても、自分で見ても、なぜずれるのか分からない。

転機は、エージェントに「目」を与えることを思いついたときでした。

## 透明テキストレイヤーとは

スキャンされたPDFは、本質的には画像です。文字に見えていてもビットマップなので、そのままでは検索もコピーもできません。

これを解決するのがOCRで、エンジンが画像中の文字を認識し、位置情報とともに透明なテキストレイヤーとして重ねます。

```
┌─────────────────────┐
│  透明テキストレイヤー  │ ← OCRで生成（目に見えない）／検索・コピーに使われる
├─────────────────────┤
│   スキャン画像        │ ← ユーザーに見える部分
└─────────────────────┘
```

検索するとビューアはこのレイヤーを探し、該当箇所をハイライトします。つまりレイヤーの位置がずれていると、ハイライトが実際の文字と違う場所に出る。透明なので見た目には問題がなく、検索して初めて気づく——「見えない不具合」の正体です。

症状は横向きページ（`/Rotate=90` を持つページ）でだけ発生していました。

## 苦戦 — 座標の数値だけを見ていた

調査をAIエージェントに任せると、OCR結果のテキスト座標とページ寸法を比較し、座標のスケーリングがずれているという仮説を立てました。スケール補正を施すと「位置」は改善したように見える。しかしハイライトのずれは根本的に解消しません。

エージェントは座標を調整し続け、私もPDF仕様を読み込みましたが、進まない。

後から振り返ると、**両方とも座標（数値）だけを見ていた**のが問題でした。透明テキストは目に見えないので、テキストの向きやサイズが正しいかを確認する手段がなかったのです。

## 転機 — エージェントに「目」を与える

検証結果を確認できないのが問題なら、確認できるようにすればいい。透明テキストを半透明にして、エージェントが「見て」判断できるようにする。

やることは1行です。

```ruby
# HexaPDF 0.35.1 / Ruby 3.2
canvas.save_graphics_state do
  canvas.opacity(fill_alpha: 0.5, stroke_alpha: 0.8)  # 0.0（完全透明）から変更
  canvas.fill_color(255, 0, 0)                        # 赤で可視化
  canvas.font(font, size: font_size)
  canvas.text(text, at: [x, y])
end
```

レンダリングすると、数値では気づけなかったことが一目瞭然になりました。

`/Rotate=0` のページでは赤いテキストが元の位置に正確に重なっている。ところが `/Rotate=90` のページでは、テキストレイヤーが縦書きで表示され、サイズも全く違う。座標が「ある程度正しい位置」にあっても、向きが90°ずれていればハイライトは合いません。座標調整を繰り返しても解決しなかった理由が、ここで分かりました。

## 原因 — 2つの座標系のミスマッチ

`/Rotate` は表示時にページを回転する角度の指定で、重要なのは内部の座標系（MediaBox座標系）は回転しないことです。

クラウドのOCRサービス（画像を渡すと文字とその座標を返すAPI）は、PDFを画像として認識します。`/Rotate=90` のPDFを画像化すると横長の画像になるので、返ってくる座標は表示座標系に基づきます。

一方 HexaPDF の `canvas.text(at: [x, y])` はMediaBox座標系で描画します。

| 座標系 | 原点 | 回転 | 使用箇所 |
|---|---|---|---|
| MediaBox座標系 | 左下 | 適用されない | PDF描画ライブラリ |
| 表示座標系 | 左上 | `/Rotate` 適用済み | OCRサービスの返す座標 |

`/Rotate=0` では両者が一致するため問題になりません。`/Rotate≠0` でだけ、位置と向きが狂います。

## 修正 — CTM（座標変換行列）

最初に試した `canvas.rotate(90)` は回転のみで原点移動を行わないため、向きは合っても位置がずれたままでした。

正しくは `canvas.transform` に座標変換行列を渡します。CTMは6つのパラメータで回転・スケーリング・平行移動を一度に表現できます。

```ruby
rotation = original_page[:Rotate] || 0
if rotation != 0
  mb = original_page.box(:media)
  mb_w, mb_h = mb.width.to_f, mb.height.to_f
  cv_w, cv_h = ocr_page.width.to_f, ocr_page.height.to_f

  case rotation
  when 90
    sx, sy = mb_h / cv_w, mb_w / cv_h
    canvas.transform(0, sx, -sy, 0, mb_w, 0)
  when 180
    sx, sy = mb_w / cv_w, mb_h / cv_h
    canvas.transform(-sx, 0, 0, -sy, mb_w, mb_h)
  when 270
    sx, sy = mb_h / cv_w, mb_w / cv_h
    canvas.transform(0, -sx, sy, 0, 0, mb_h)
  end
end
```

追加は22行。`/Rotate=0` のパスには一切変更を加えていないため、リグレッションリスクは最小です。

## 検証

PyMuPDFで4ページ（0°/90°/180°/270°）のサンプルPDFを生成し、四隅と中央にマーカーを置いて、修正前後を半透明可視化で比較しました。0°は変化なし、90°/180°/270° はいずれも正しい向き・位置に配置されることを確認しています。

合成データだけでは実際のスキャン文書の多様さを覆えないので、実運用のOCR処理済みPDFからランダムにサンプリングして追加検証もしました。**合成データは「自分が想定した異常」しか含みません。** 想定外の組み合わせを踏むかどうかは実物でしか分かりません。

## 学び — AIが陥る「数値だけで判断する罠」

エージェントは座標だけを見て問題を解こうとしました。座標が「だいたい合っている」ように見えると、そこで満足してしまい、向きやサイズという視覚的な情報を見落とす。

これは「見えないもの」を扱う際の典型的な落とし穴だと思います。数値やログだけでは捉えきれない問題があり、それは人間の「見てみよう」という直感で初めて露わになる。

私が伝えたのは「テキストレイヤーを可視化してみて」の一言だけでした。その後のエージェントは、原因分析からCTM導出、サンプル生成、全パターン検証までを高速に実行しています。報告されたのは90°の1パターンだけでしたが、180°/270° も同時に洗い出して対応しました。

### 想定される反論

「可視化のアイデアをAIに出させることもできたのでは」

できたかもしれません。ただ、「行き詰まったら観測手段を増やせ」と指示するのも人間です。何をもって解決とするのか、その道筋をどう検討するのか。それを考えさせる指示自体を、こちらが出しています。可視化という一手を誰が思いついたかより、そこを詰める役が誰かのほうが本質だと思っています。

「座標系の変換は定石で、仕様を読めば可視化なしで分かったのでは」

仕様どおりに動いているなら、そのとおりです。実際は違いました。仕様の記述と、実装が積み上げてきた処理が絡んでいて、仕様を把握しただけでは判断できない。仕様を読んだうえで、実際の稼働状況と、そこから出てきた結果を見て判断する必要がありました。可視化は、その結果を見るための手段です。

「実物のサンプリングは足りているのか」

相当数を見ています。人の手では終わらないので、バックテストとしてスクリプトとAIを組み合わせて回しました。合成データで全パターンを作り、実物で想定外を拾う。片方だけでは埋まらない穴を、二段構えで埋めています。

方向性を示すのは人間、実行力を発揮するのはAI。 ただ、この役割分担がいつまで有効かは分かりません。「見てみよう」に相当する発想をエージェント側が持てるようになれば、この記事の教訓は古くなります。そのほうが望ましいとも思っています。

## まとめ

- 透明テキストレイヤーのバグは、見た目が正常なため通常のテストでは検出できない。
- 数値だけを見ていると向きとサイズの異常を見逃す。半透明化して可視化すれば一目で分かる。
- 原因はOCRが返す表示座標系とPDF描画ライブラリのMediaBox座標系のミスマッチ。`/Rotate=0` でだけ偶然一致する。
- `canvas.rotate` では足りず、CTM で回転と原点移動を同時に表現する。
- 合成データは「自分が想定した異常」しか含まない。実データでの検証を省かない。
