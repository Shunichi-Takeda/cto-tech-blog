# スキャンPDFのOCRが「読めない」3つの理由 — エンジンを変えても直らない話

OCRが期待通りに動かないとき、最初に疑うのは認識精度だと思います。私もそうでした。そしてエンジンの比較検討を始めようとして、手が止まりました。

**失敗の大半が、認識精度の問題ではなかった**からです。

切り分けると3類型に分かれました。どれも、エンジンを差し替える前に潰せるものでした。

## 類型1: 回転メタデータを無視している

PDFのページには `/Rotate` があり、0/90/180/270 のいずれかを持ちます。スキャナや複合機が出力したPDFでは、画像は横倒しのまま、表示時に回転させる形になっていることがよくあります。

このとき画像をそのままOCRにかけると、回転量ごとに症状が違います。

| `/Rotate` | 症状 |
|---|---|
| 90 | 横書きのはずのテキストが縦書きとして認識され、座標もずれる |
| 180 | テキストが上下逆に配置される |
| 270 | 90と逆方向の縦書きとして認識される |

見落としやすいのは、文字が全く読めないわけではない点です。エンジンは律儀に何かを返してくる。返ってきた文字列だけを見ていると「精度が低い」と解釈して、原因を取り違えます。

判定は、抽出前にページ属性を見るだけです。

```python
# pypdf 5.x
from pypdf import PdfReader

for i, page in enumerate(PdfReader("scanned.pdf").pages):
    rotate = page.get("/Rotate", 0) or 0
    if rotate % 360 != 0:
        print(f"page {i}: /Rotate={rotate} → 前処理で正立させる必要あり")
```

対策は、OCRに渡す前に画像を正立させること。表示上の見た目を信じず、属性を読んで前処理で潰す。これを入れると、精度改善を目的としたエンジン比較そのものが不要になる場合があります。

## 類型2: 空白ページでページ番号がずれる

複数ページを処理して、抽出結果をページ単位で保持する設計はよくあると思います。「3ページ目の本文はこれ」という対応があれば、検索結果から原文へ飛べるので。

ここに空白ページが混ざると壊れます。原因は、「OCR結果があったページ」の連番を「PDFのページ番号」として扱ってしまうことです。

```python
# NG: 結果が返ったページだけを詰めるとインデックスがずれる
for page in pages:
    text = ocr(page)
    if text.strip():
        results.append(text)          # ← 空白ページの分だけ後続が前にずれる

# OK: PDFのページ番号を明示的に持ち回る
for page_number, page in enumerate(pages, start=1):
    results.append({"page": page_number, "text": ocr(page)})   # 空でも席を残す
```

書いてしまえば当たり前です。厄介なのは発見のされ方で、この不具合は「読めない」という形では現れません。文字は取れているので抽出処理のテストは通る。気づくのは、検索から原文へ飛んだ人が「別のページが開く」と言ったときです。

しかも1ページ目の空白では起きません。空白が中間にあるファイルでだけ再現します。「中間に空白ページを含む複数ページのスキャンPDF」がテストデータとして用意される確率は低い。ここは反省点で、境界データの用意が甘かったと思っています。

## 類型3: 監視が正常な処理を失敗と判定する

3つ目はOCRの話ですらありません。ただ症状は「大きいファイルを入れるとOCRが失敗する」という形で観測されます。

長時間かかる処理には生存確認を入れます。「一定間隔で進捗を更新し、途絶えたら異常とみなす」という定番の設計です。問題は、その間隔より1ステップの処理時間が長くなったときに起きます。

```
[監視] 5分ごとに進捗の更新を確認 → 更新がなければ失敗と判定
[処理] ページ数の多いファイルを処理中。更新まで5分超
         → 正常に動いているのに失敗判定され、強制終了される
```

小さいファイルでは絶対に再現しません。負荷が上がるほど、つまり本番で重要な処理ほど落ちます。

対策は2方向あります。タイムアウト値を伸ばすのは対症療法で、いつかまた超える。採るべきは進捗の更新粒度を細かくするほうです。ファイル単位ではなくページ単位で「生きている」と申告させれば、総処理時間がいくら伸びても誤判定しません。生存監視は「全体が終わったか」ではなく「進んでいるか」を見るべきもので、前者を見ていたのが設計の誤りでした。

## 3類型に共通していること

3つとも、OCRエンジンの外側にあります。類型1は前処理の欠落、類型2はページ管理の設計ミス、類型3は監視設計の前提ミス。

にもかかわらず、ユーザーから見ると全部「OCRが読めない」という同じ症状で報告されます。だから最初にエンジンの精度を疑ってしまう。手を止めて切り分けを先にやったのは結果的に正解でしたが、正直なところ、あのままエンジン比較の検証環境を作り始めていた可能性は十分ありました。

**症状の名前（OCRが読めない）を、原因の場所（OCRエンジン）と混同しない。** ユーザーの言葉は症状であって、診断ではありません。

## 想定される反論

「最新のエンジンやLLM-OCRなら、回転も空白も吸収するのでは」

吸収するものもあると思います。そこは否定しません。ただ、今回はその比較検証に時間を使いませんでした。目の前に読めなくて困っている利用者がいる状況で、どのエンジンなら直るのかを研究的に詰めていくと、ペインが解消されるまでの時間がそのぶん延びます。

先に切り分けをやったら、3つのうち2つはエンジンの外側にあり、渡す前に潰せるものでした。だから「まずエンジンの外を直す」を選んでいます。ここに書いたのは、その選択の結果として見えたものです。差し替えれば直る類型があるかどうかは、確かめていません。

「前処理を自前で持つより、エンジン側の機能に寄せたほうが保守が楽では」

エンジン側の吸収は当てにできない、というのが正直なところでした。機能として提供されていても、どういう条件でどう効くかをこちらで制御できるとは限りません。判断したのは、作れるかどうかではなく、自分たちで運用できるかどうかです。前処理は自分で書いた分だけ挙動が読めるので、想定と違ったときに追えます。

「3類型で網羅できているのか」

網羅ではありません。乱筆な手書きや低解像度で読み取れないものもありました。ただそれらは、OCRの性能限界として利用者に納得してもらえる範囲であれば、失敗として数えていません。ここで扱っているのは「本来読めるはずのものが読めない」失敗です。

確認したのはまとまった件数のOCR結果で、全部を目で見るわけにはいかないのでAIとスクリプトを併用しました。全件を人が見るのと、サンプルだけ見るのとの中間で、手間と時間の折り合いをつけた形です。

## 縦書きについて

結論が出ていない話も書いておきます。縦書きです。

新聞や古い文書のような縦書き原稿は、上記3類型とは別に、そもそも認識自体が難しい領域です。とくに縦書きと横書きが同一ページに混在するレイアウトは、主要なクラウドOCRサービスでも取りこぼしが報告されています（[検証例](https://zenn.dev/chot/articles/6587f0a517fb25)）。

ここは前処理では解決しないので、「対応範囲外」と線を引くか、レイアウト解析を別途噛ませるかの判断になります。まだ検証中で、どちらを採るか決めていません。決めたら書きます。

## まとめ

- スキャンPDFのOCR失敗は、エンジン精度ではなく周辺の3類型に分かれることが多い。
- 類型1: `/Rotate` を無視して画像をそのまま渡している。抽出前に属性を読んで正立させる。
- 類型2: 空白ページを詰めて連番にし、PDFのページ番号とずれる。空ページも席を残す。
- 類型3: 生存監視の間隔より1ステップが長く、正常処理が失敗判定される。監視は「終わったか」ではなく「進んでいるか」を見る。
- 症状の名前と原因の場所を混同しない。報告は症状であって診断ではない。
