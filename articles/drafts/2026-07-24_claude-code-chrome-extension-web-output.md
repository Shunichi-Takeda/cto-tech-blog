# AI活用の知見をClaude内に閉じ込めない — Claude Codeと実Chromeを『相乗り』させる

ファイルやコードの作業はAIに任せられるようになりました。ところが材料がログイン必須のWebサービスの向こう側にあると、そこだけ手が届かない。結局、自分でブラウザを開いてコピペしてAIに貼る、という手作業に戻ります。

「ログインの壁」を、Claude Codeと普段使いのChromeを同じセッションでつなぐことで越えた話です。読み取りだけでなく書き込みもできるので、AIで得た知見をClaudeの中に閉じ込めず、そのままWebへ出力するところまで一気通貫になりました。

## Claude Codeには2つのブラウザ系統がある

ここの使い分けが出発点でした。

| | 内蔵ブラウザ<br>`mcp__Claude_Browser__*` | Claude in Chrome<br>`mcp__claude-in-chrome__*` |
|---|---|---|
| 実体 | Claudeが持つ**隔離ブラウザ** | **自分の実Chrome**（拡張機能経由） |
| ログイン状態 | 都度ログインが必要 | **既存のログインセッションをそのまま利用** |
| 向く用途 | 外部サイトの閲覧・検証 | ログイン必須の社内サービス操作 |

外部サイトを見るだけなら内蔵ブラウザで足ります。ただログイン必須のサイトだと毎回ログインからやり直しで、地味に待たされる。DB経由で本文を引く方法も試しましたが、ID解析や接続手順が重く、「記事本文を読む」には過剰でした。

**ファイル作業はAIに委譲できているのに、認証の壁の向こう側だけ届いていない。** この非対称が気持ち悪かった。

## つなぎ方

拡張を入れて同じアカウントで接続したら、Claude側が毎セッション開始時にやるのは3つのツールを順に呼ぶだけです。

```text
1. list_connected_browsers   … 接続中の実Chromeを確認（deviceId を取得）
2. select_browser {deviceId} … 対象Chromeを選択
3. tabs_context_mcp {createIfEmpty: true} … 操作用タブを確保
```

あとはURLを渡すだけ。

```text
4. navigate {url}   … 対象タブでページを開く
5. get_page_text    … レンダリング済みの本文をプレーンテキストで取得
   （構造や入力欄が要るときは read_page {filter: "interactive"}）
```

重要なのは、認証をClaudeが一切触らないことです。すでにログイン済みのChromeに相乗りするので、パスワードはClaudeに渡りません。

正直、これぐらいでいいのか、と拍子抜けしました。認証の壁をどう越えるかをずっと難問だと思っていたのに、越えずに相乗りするだけで済んだ。意外なほど簡潔な解でした。

## 読むだけでなく書き戻す

効きどころは、読み取りで終わらないことです。

```text
1. read_page {filter: "interactive"} または find で入力欄を特定
2. form_input {ref, value} もしくは computer {action: "type", text}
3. 【保存の直前】入力内容をユーザーに提示し、承認を得てから保存
```

「調査（Web読み取り）→ ファイル編集・Git → Webへ書き戻し」を、1セッションの中で行ったり来たりできます。人間がコピペで仲介する切り替えコストがありません。

正直、この効果は想像以上でした。社内SaaSの取得手段を一本化する作業の最中に「これ、読み取りだけじゃなくて書き込みまで同じセッションでできるじゃないか」と気づいたのが、この記事の発端です。知見がClaudeの中に閉じず、そのままWebの共有先へ出ていく感覚は、体験してみると効きます。

## ハマりどころ

失敗ベースで残します。

- **`deviceId` を決め打ちしない**。拡張の再接続やChrome再起動で変わります。毎回 `list_connected_browsers` で取り直す。
- **開始時に必ず `tabs_context_mcp` を呼ぶ**。タブはブラウザを閉じない限り残りますが、Claude側は会話開始時点でどのタブがあるかを知りません。「新規タブ作成が必須」ではなく「開始時の現状確認が必須」です。
- **タブは増やさず1枚を使い回す**。`navigate` でURLだけ差し替えるのが軽い。会話ごとに新規タブを作るとタブが無限に増えます。
- **エディタの見出し自動整形はやらせない**。これは事故りました。Webエディタでスタイルを当てる操作は行の範囲選択（`triple_click` 等）を伴い、座標が1行ズレると**別の段落を巻き込んで本文を壊します**。「1行ズレたら破壊的」な操作は、AIにやらせず人間の手に残すのが結局いちばん安全でした。

## 安全設計 — 読み取りは即時、書き込みは人間の承認

実Chromeは自分のログイン権限そのもので動きます。だからこそ操作を切り分けました。

- **読み取り**: ユーザー確認なしで実行してよい
- **書き込みの確定**（保存・公開・投稿・送信）: 後戻りしにくいので、内容を提示し**明示的承認を得てから**
- **ログイン・認証・パスワード入力**: AIは行わない。切れていたらユーザー自身がログインする
- **見えてはいけないタブを巻き込まない**: 自分に見えるものは全部見える、ということ。作業用タブに閉じる

要は「読み取りはAI、書き込みの確定は人間」。この一線を引くだけで、実ブラウザ操作の怖さはかなり抑えられます。

### それでも残る4つの疑問

この構成を人に話すと、だいたい同じところを聞かれます。

「自分のログイン権限をAIに使わせて大丈夫なのか」

前提を4つ置いています。読み取れるのはこちらが提示したサイトだけで、Chromeの全タブを勝手に舐めるわけではないこと。ブラウザは目の前で動き、何をしているかが画面に出続けること。そして触れる範囲は、そもそも自分がその権限で見られる範囲を出ないこと。加えて、利用しているAIエージェントが組織の契約として学習に使わないことを保証できていること。

そのうえで、漏洩のリスクと業務品質を天秤にかけました。得られるものに対してリスクは小さいという判断です。逆に言えば、この4つのどれかが崩れる環境では同じ判断はしません。

「APIがあるならAPIを使えばいいのでは」

APIがあるなら使います。この手段が要るのは、APIが公開されていないサービスを相手にしているときや、本番データベースへの経路が込み入っていて、そこまで潜るコストが目的に見合わないときです。

欲しいのが画面に出ているテキスト、たとえば指示文や調査結果そのものだけなら、表示されている画面を読むほうが早くて安い。データの正本が要る作業と、表示されている情報で足りる作業を分けて考えています。

「何をしたのか、後から追えるのか」

エージェント側の指示に、何をしたか・なぜしたかを提示させる工程を組み込んでいます。チャットで回答の根拠を問い返すのと同じ発想で、操作前後に確認のゲートを置く形です。

ブラウザ側の操作ログに頼るのではなく、指示の設計で担保する。ここは仕組みで固めているというより、運用で成立させている部分です。

「拡張の仕様が変わったら止まるのでは」

止まりません。この方法は人の手の代替の範疇に収まっているので、動かなくなればその作業を人が手でやるだけです。業務そのものは止まりません。

止めたくないなら、スクレイピングのスクリプトを組んで維持する道もあります。ただそれは、止まるリスクと維持コストを天秤にかける話になります。今のところ、天秤は代替手段を持たない側に傾いています。

## 学び

「相乗り」は認証の壁を越える汎用パターンです。特定のSaaSに限らず、ログインが要るあらゆるWebサービスに応用できます。認証を代行させないのがポイントで、これによって「認証はユーザー、操作はAI」という責任分界が自然に決まります。

そして、**入力より出力を自動化したときのほうが効果が跳ねました**。エージェントの高速化は入力側（材料集め）に目が行きがちですが、出力側を同じセッションに載せると知見が滞留しなくなります。

一方で、危険な操作をあえて人間に残すのが安全に回すコツだとも思っています。全部を自動化しようとせず、「1行ズレたら壊れる」種類の操作は境界の外に置く。ここの線引きをどう一般化するかは、まだ言語化できていません。今のところ「破壊が不可逆かどうか」で判断していますが、もう少し良い基準がありそうです。

## まとめ

- Claude Codeには「内蔵の隔離ブラウザ」と「実Chromeを操作する拡張」の2系統があり、ログイン必須の社内Webには後者が向く。
- 接続は `list_connected_browsers` → `select_browser` → `tabs_context_mcp` の3つで確認し、あとは `navigate` + `get_page_text` / `form_input` で読み書きする。
- `deviceId`/`tabId` は毎回確認、タブは使い回し、見出し整形など破壊的操作は人間に残す。
- 読み取りは即時、書き込みの確定は人間の承認。この一線で安全に運用できる。
