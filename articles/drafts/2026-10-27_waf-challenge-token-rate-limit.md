# IPを使い捨てる攻撃者に、IP単位のレート制限は効かない — AWS WAF Challengeとトークン単位の制限

ログインAPIへの攻撃を、AWS WAF のレート制限で止めています。数え方はIPごとではなく、ある範囲のログイン試行を全体で1つの枠として数える方式です。

攻撃は止まります。その代わり、攻撃が続いている間は、同じ範囲に入る正規ユーザーも全員止まります。

これを解くために、AWS WAF の Challenge を通った正規クライアントだけを枠の外へ出そうとしました。ところが「Challengeを通ったら許可」という前提は、公式の仕様にありませんでした。さらに、迂回路を作るとそこが新しい穴になります。最終的に、トークン単位のレート制限を迂回路の手前に置く構成になりました。

![仮面のようにIPを付け替える攻撃者を全体の門で止め、札（トークン）を持った正規ユーザーだけが数を数える小さな門を通る様子のドット絵](/images/waf-challenge-token-rate-limit/overview.png)

なお、本番への適用はこれからです。この記事に書けるのは、仕様の確認と検証環境で確かめたこと、設計上の判断までです。

## IPごとに数えないのは、IPが使い捨てだから

設計を見直す途中で「全体で1つの枠だと正規ユーザーが巻き添えになるので、IPごとに数え直してはどうか」という案が出ました。採りませんでした。

攻撃側は、IPアドレスを使い捨てにして試行してきます。IPごとに数えると、1つのIPあたりの試行は数回で終わり、どのIPも上限に届きません。上限が攻撃者を一度も止めないまま、正規ユーザーだけが「IPごとの上限」という制約を受けることになります。

全体で1つの枠にすると、攻撃の総量で枠が埋まり、攻撃は止まります。巻き添えは、その代償です。

```json
"RateBasedStatement": {
  "Limit": 100,
  "EvaluationWindowSec": 300,
  "AggregateKeyType": "CONSTANT",
  "ScopeDownStatement": { "...": "ログインAPIの、ある範囲のリクエスト" }
}
```

`AggregateKeyType: CONSTANT` は、条件に一致したリクエストをすべて1つのカウンタで数える指定です。値は例で、実際のしきい値や範囲の条件はここには書きません。

問題は数え方ではありませんでした。正規ユーザーを、攻撃者と同じ枠に入れていることが問題です。

## 「Challengeを通ったら許可」は、仕様に書かれていない

正規クライアントと攻撃者を分ける手段として、AWS WAF の Challenge を選びました。画面に何も出さない JavaScript の検査で、通過するとトークンが発行されます。Web とデスクトップは `challenge.js` で、モバイルは AWS の SDK でトークンを取り、ログインのリクエストに `x-aws-waf-token` ヘッダーで付けて送ります。

当初の設計は「Challengeを通過したリクエストは許可」でした。ところが公式ドキュメントには、有効なトークンを持つリクエストに対して、Challenge は Count と同じように振る舞い、残りのルールで評価を続けると書かれています。

つまり Challenge ルールを1本足しただけでは、トークンを持った正規ユーザーも、後ろのレート制限まで流れて同じ枠で止まります。設計の前提が、ここで崩れました。

直し方は、Challenge ルールで自前のラベルを付け、そのラベルを条件にした許可ルールを、レート制限の手前に置くことです。

```json
{
  "Name": "challenge-signin",
  "Priority": 10,
  "Statement": { "...": "ログインAPI、かつクライアントがトークンを付けたことを示すヘッダーあり" },
  "Action": { "Challenge": {} },
  "ChallengeConfig": { "ImmunityTimeProperty": { "ImmunityTime": 300 } },
  "RuleLabels": [ { "Name": "example:signin:challenge-passed" } ],
  "VisibilityConfig": { "...": "..." }
}
```

AWS側のラベル（`awswaf:managed:token:accepted`）を使う案もありました。ただ、このラベルは Bot Control などのマネージドルールを通ったときにしか付きません。許可ルールがマネージドルールの並び順に左右されるのを避けたかったので、自前のラベルにしました。

## 迂回路を作ると、そこが新しい穴になる

許可ルールで枠の外へ出すと、今度は別の問題が生まれます。攻撃者が有効なトークンを1つでも手に入れれば、そのトークンを使い捨てのIPに配り、上限なしにログインを試せてしまいます。

IPは使い捨てにできても、トークンは Challenge を解かないと手に入りません。そこで、許可ルールの手前に、トークンの値ごとに数えるレート制限を置きました。

```json
"RateBasedStatement": {
  "Limit": 100,
  "EvaluationWindowSec": 300,
  "AggregateKeyType": "CUSTOM_KEYS",
  "CustomKeys": [
    { "Header": { "Name": "x-aws-waf-token",
                  "TextTransformations": [ { "Priority": 0, "Type": "NONE" } ] } }
  ],
  "ScopeDownStatement": {
    "LabelMatchStatement": { "Scope": "LABEL", "Key": "example:signin:challenge-passed" }
  }
}
```

並びはこうなります。

```
Challenge（無効なトークンは止める。有効ならラベルを付けて次へ）
  ↓
トークン単位のレート制限（ラベルあり。1トークンあたりの上限）
  ↓
許可（ラベルあり。全体の枠を消費しない）
  ↓
全体で1つの枠のレート制限（従来どおり）
```

正規ユーザーが1つのトークンで、短時間に何度もログインを試すことはありません。攻撃者は量を出そうとすると、Challenge を解き続けることになります。そのコストが抑止になる、という読みです。

許可ルールには「トークンがヘッダーにあり、かつ Cookie には無いこと」という条件も足しました。Cookie に有効なトークンを入れ、ヘッダーには毎回でたらめな値を入れると、トークン単位の集計キーを毎回変えられるおそれがあるためです。両方にトークンがあるとき WAF がどちらを使うかは、公式ドキュメントに書かれていませんでした。分からないものは、許可しない側に倒しています。自社のクライアントはどれもヘッダーで送るので、正規ユーザーには影響しません。

## 書いてから気づいた落とし穴

設計を固める途中で、仕様と実装の食い違いがいくつも出てきました。数えると6つです。

1. ブラウザの事前確認（OPTIONS）が止められる。Web とデスクトップのログインは独自ヘッダーを付けるので、ブラウザは本番のPOSTの前に OPTIONS を送ります。OPTIONS にはトークンが付かないため、攻撃中は全体の枠で止まり、トークンを持っていてもログインできません。全体の枠の対象から OPTIONS を外しました。OPTIONS は認証情報を持たないので、外しても穴にはなりません。
2. `TokenDomains` を先に設定しないと、Web の全員が止まる。Web はトークンを画面側のドメインで取得し、APIのドメインへ送ります。`TokenDomains` が無いとドメイン不一致で拒否されます。リリースの順番を固定しました。
3. Challenge の応答には CORS ヘッダーが付かない。ブラウザは応答の中身を読めず、通信エラーとして扱います。Web で「Challenge で止められた」専用のダイアログを出そうとしても、実際には出ません。
4. `ImmunityTime` の書き場所。設計書では `Action.Challenge` の中にありましたが、APIではルール直下の `ChallengeConfig` です。そのまま適用するとエラーになります。
5. `update-web-acl` は、渡さなかった項目を消す。既存のカスタム応答の本文（`--custom-response-bodies`）も毎回一緒に渡す必要があります。
6. `challenge.js` は 687KB あった。トークンが要るのはログインのときだけなので、ログイン済みのユーザーには読み込ませないよう依頼しました。

書式は、適用前に読み取り専用の `check-capacity` で確かめました。

```bash
aws wafv2 check-capacity --scope REGIONAL --rules file://rules.json --region ap-northeast-1
```

ラベル名を短い形で書いてよいか、`ChallengeConfig` の構造、Cookie を対象にしたサイズ条件の書き方は、ここで通りました。WCU の上乗せは数%で、無料枠の 1,500 には収まっています。

## Count から始める段階リリースは、この構成では危ない

リリースの進め方について、私の最初の案は「Challenge は当初 Count のみにして、トークンが無くても通過させる。段階的にリリースすべき」でした。

段階的に出すこと自体は正しいのですが、Challenge だけを Count にして許可ルールを有効にしたままにすると、穴が開きます。ラベルは条件に一致した時点で付くので、Count の Challenge は、トークンを検査せずにヘッダーのあるリクエストすべてにラベルを付けます。偽のヘッダーを付けるだけで、全体の枠を迂回できてしまいます。

しかも Count のルールは一致を数えるだけで、トークンが有効かどうかは観測できません。

決めた段階は3つです。

| 段階 | Challenge | トークン単位の制限 | 許可 | 見るもの |
|---|---|---|---|---|
| 1 | Count | Count | Count | ヘッダー付きの件数、迂回していたら何件か |
| 2 | 有効 | 遮断 | Count | 無効なトークンが止まるか |
| 3 | 有効 | 遮断 | 有効 | 正規ユーザーが枠を迂回できるか |

許可ルールを有効にするのは、Challenge が実際にトークンを検査するようになってからです。**切り戻しは逆の順で行います。** 先に許可を止め、その後で Challenge を止めます。順番を逆にすると、短い時間ですが同じ穴が開きます。

## 検証環境で確かめられること、確かめられないこと

検証環境には、本番の全体の枠に当たるルールがありませんでした。そのままでは「Challenge を通ったリクエストが枠に引っかからない」ことを確かめられません。範囲の条件を外した一時ルールを足して、巻き添えを再現しました。

確かめたかったのは次の5点です。

- 全体の枠を埋めた状態でも、新しいクライアントからはログインできる
- 同じトークンを使い回すと止まる
- Cookie だけでトークンを送ると、全体の枠に回る
- OPTIONS が枠を消費しない
- 偽造したトークンは止まる

検証が済んだら、一時ルールは消し、Challenge の3本は本番に合わせて残す方針にしました。ただし、トークン単位の上限は検証環境だけ緩めます。テストでログインを連続で消化すると上限に当たり、それを不具合と見間違えるためです。本番と値が違うことは「検証環境と本番の差分」として記録しました。検証環境の結果を、本番の挙動の根拠にしないためです。

遮断されたときの画面表示をそろえるため、遮断の応答に CORS ヘッダーを足す案も出ました。これは見送っています。攻撃はブラウザを通らずAPIを直接叩いているので、CORS ヘッダーは攻撃側の見え方を何も変えません。変わるのは正規ユーザーの表示だけで、レート制限で止まった人に別の理由のエラーを見せると、問い合わせや誤った対処を招きます。表示を直すなら、WAF ではなくクライアント側の仕事です。

## 想定される反論

「全体で1つの枠のままでは、攻撃中に正規ユーザーを止め続ける。枠の設計そのものを変えるべきでは」

枠の数え方を変えると、攻撃を止められなくなります。IPを使い捨てにしてくる相手には、IPごとの枠は一度も上限に届きません。攻撃を止めているのは、全体で1つの枠だからです。

巻き添えは、枠の設計の問題ではありませんでした。正規ユーザーと攻撃者が、同じ枠に入っていることが問題です。だから枠はそのままにして、正規ユーザーの方を枠の外に出すことにしました。この記事の構成は、そのためのものです。

巻き添えになるのは、枠の範囲に入る利用者に限られます。範囲の外の利用者は、攻撃中もログインできていました。

「Challenge は自動操作されたブラウザでも解ける。抑止として弱いのでは」

解けます。Challenge を、攻撃者を完全に止める壁だとは考えていません。

狙っているのはコストです。今来ている攻撃は、ブラウザを通らずにAPIを直接叩いています。Challenge を解くには、ブラウザでスクリプトを実行する必要があります。しかも1つのトークンで試せる回数には上限を置いたので、量を出したければ Challenge を解き続けることになります。1回の試行にかかる手間が、APIを直接叩くときより一段重くなります。

壁ではなく、通行料です。払い続けてでも攻めてくる相手が出てきたら、そのときは別の手を考えます。

「Challenge は追加料金がかかる。費用に見合うのか」

課金は、Challenge を実行した回数に応じて増えます。対象はログインAPIで、しかもクライアントがトークンを付けたことを示すリクエストだけに絞っているので、課金されるのはほぼログインの回数分です。サイト全体の通信に Challenge をかけるのとは、桁が違います。

比べたのは、攻撃が来ている間、枠の範囲の正規ユーザーがログインできないことです。ログインできなければ、その間はサービスを使えません。ログインの回数分の課金で、それを避けられるなら見合う、と判断しました。

## まだ決めていないこと

`ImmunityTime` を300秒のままにするかは決めていません。アプリをバックグラウンドに置くとトークンの自動更新が止まるので、復帰直後に古いトークンでログインすると止まる可能性があります。延ばせばこの問題は減りますが、1つのトークンで試行できる期間も延びます。検証環境のアプリで、バックグラウンドに置いてから復帰する動作を確かめてから決めます。

段階1の計測が、Bot Control がヘッダーで送られたトークンも判定する前提に立っている点も、まだ確かめていません。

## まとめ

- IPを使い捨てる攻撃者には、IP単位のレート制限が効かない。全体で1つの枠にすると攻撃は止まるが、正規ユーザーも巻き添えになる。
- AWS WAF の Challenge は、有効なトークンでも Count と同じ扱いで、後続のルール評価が続く。許可したいなら、ラベルを付けて許可ルールを別に置く。
- 迂回路を作ったら、迂回路にも上限を置く。IPは使い捨てにできても、トークンは Challenge を解かないと手に入らない。
- Challenge を Count から始める段階リリースは、許可ルールと組み合わせると穴になる。許可は最後に有効にし、切り戻しは逆順で。
- 検証環境と本番の差分は記録しておき、検証環境の結果を本番の根拠にしない。
