# 「検証環境は1つで足りる」を撤回した — 課題ごとに作って消すプレビュー環境

最初に決めた「検証環境は1つでいい、自動化なんだから直列で回せば足りる」という設計は、実案件で1件通したその日に撤回しました。

いまは、課題管理ツールの課題キーを1つ渡すと、その課題専用の環境が10分ほどで立ち上がります。課題が完了すれば、環境は自動で消えます。

![課題ごとに環境を作り、完了したら消す流れと、1つを使い回すと混ざるが、課題ごとに分ければ混ざらない、という見どころのドット絵](/images/per-issue-preview-environments/overview.png)

同じ日に、もう1つ分かったことがあります。止めていたはずの環境の固定費のおよそ96%は、使っていない期間に待機していたロードバランサーでした。

前編（AIに会社を教える話）で書いた「概要設計からSTGテストまでを通しで回す」流れの、最後の工程の話です。

## 「直列で回せばいい」と決めた理由

設計からコーディング、Draft PR の作成まではAIエージェントに任せられるようになっていました。止まるのは、その Draft PR を動かして確かめる場所です。共有の検証環境に載せると、他の案件の確認とぶつかります。

そこで9月の頭に、Draft PR を `develop + PR` の状態で反映した STG 相当の環境を自動で作る設計を始めました。最初に置いた前提は3つです。

- 環境は1つ。自動化なので、試験は直列に並ばせれば足りる
- 作るのは構築基盤だけ。アプリケーションのコードには手を入れない
- 確かめられないことは、確かめられないと明示する

2つ目と3つ目は、いまも変えていません。アプリのコードを触らない代わりに、検索基盤へのテストデータの再投入はやめました。検索がヒットするかの確認は、この環境では「対象外」に数えています。判定は OK / NG / 対象外（環境制約）/ 実施不可 の4値で、黙って落とすことだけはしないようにしました。

起動のきっかけも、当初は Draft PR に専用のラベルを付けたら動く案でした。ただ、その PR に push するたびに更新と試験が多重に走ります。デバウンスとコミットの照合で抑える設計まで書いたものの、採りませんでした。いまは課題キーを起点に、エージェントが自分で起動します。

## 1件通したら、前提が崩れた

9月に一通り作ったあと、しばらく間が空き、10月20日に実案件で初めて使いました。その日のうちに出した要望は次のとおりです。

- 課題ごとに環境を作る
- 課題が完了になったら環境も閉じる
- コンテナやスタックの名前に課題番号を付けて、消し漏れを防ぐ

振り返ると、崩れる兆しは最初の設計の日にありました。「案件ごとにユーザーが複数要ったり、変わった権限の設定が要ったりするはず」と、自分で書いていたからです。案件ごとの前提データが要るなら、1つの環境を直列で使い回すと、前の案件のデータが次の案件に残ります。直列にすれば足りると判断したとき、このことを見落としていました。

もう1つは費用です。環境は止めていたのに、請求は止まっていませんでした。

ECS のタスクを0にしても、ロードバランサーと、それに付く公開 IPv4 アドレスの課金は続きます。最初に作ってから実案件で使うまでの約6週間、環境は止めていました。この期間の費用のおよそ96%が、待機していたロードバランサーの分でした。タスクの稼働費は数パーセントしかありません。

**止めているつもりで、止まっていなかった。** ここで「作って消す」が、費用の面からも筋になりました。

## 課題キー1つで立ち上がるまで

### 単位は CloudFormation のスタック1つ

課題ごとに、名前に課題番号を含むスタックを1つ作ります。消すときはスタックを消せば、その課題のものは一式なくなります。消し漏れを名前で追えるのは、この形にしたからです。

ロードバランサーは全環境で1つを共有し、動いている環境が1つでもあるときだけ存在させます。課題ごとのホスト名は、ワイルドカードの DNS レコードと証明書で受けます。

### 操作は GitHub Actions の workflow_dispatch に寄せる

起動・停止・削除・一覧は、1本のワークフローの入力で切り替えます。手元のエージェントからも、クラウドで動くエージェントからも、人が Actions の画面から押しても、同じ入口を通ります。クラウドの実行環境からは AWS に直接届かないため、AWS の操作はすべてワークフロー経由にしました。

```yaml
# .github/workflows/preview-env.yml（抜粋・名前は汎用化）
on:
  workflow_dispatch:
    inputs:
      action:    { type: choice, options: [up, stop, delete, status], default: status }
      issue_key: { default: '' }
      confirm:   { default: '' }   # delete のときだけ。環境名と一致しなければ消さない
      request_id: { default: '' }  # 呼び出し元が自分の実行を見分けるため

run-name: preview-env ${{ inputs.action }} ${{ inputs.issue_key }} ${{ inputs.request_id }}

concurrency:
  group: preview-env-${{ inputs.issue_key }}
  cancel-in-progress: false

permissions:
  id-token: write
  contents: read

jobs:
  env:
    runs-on: ubuntu-latest
    timeout-minutes: 50   # OIDC で得る一時認証は1時間で切れる
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/preview-github-oidc
          aws-region: ap-northeast-1
      - name: env.sh
        env:   # 入力は式でシェルに直接埋めない。埋めると注入の経路になる
          ACTION: ${{ inputs.action }}
          ISSUE_KEY: ${{ inputs.issue_key }}
          CONFIRM: ${{ inputs.confirm }}
        run: scripts/env.sh "$ACTION" "$ISSUE_KEY"
```

AWS 側のロールは、main ブランチからしか引き受けられないように信頼ポリシーで絞っています。

```json
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:my-org/preview-infra:ref:refs/heads/main"
  }
}
```

この結果、ワークフローは常に main の内容で動きます。マージ前のテストシナリオを流したいときは、ブランチ名を別の入力で渡し、決まったディレクトリのファイルだけをそのブランチから取ります。スクリプト側でも、課題キーやファイルパスの形式を確かめてから使います。

API から起動したときは、`run-name` に入れた `request_id` を実行一覧の `display_title` で探して、自分の実行を見分けます。

### DB は TEMPLATE で複製し、ID の範囲をずらす

DB は既存の検証用 Aurora クラスタの中に、課題ごとの database を1つ作ります。中身は、テスト用の前提データを積んだ雛形からの複製です。

```sql
-- 雛形から課題用の DB を作る。クラスタ内で完結し、ダンプの置き場が要らない
-- 雛形 DB への接続が0でないと失敗する
CREATE DATABASE "preview_dev42" TEMPLATE "preview_seed";
```

雛形の正本は、前提データを作るスクリプトの方です。雛形 DB は、毎回積み直すと遅いので取っておく写しにすぎません。

ここで1つ、複製しただけでは足りない点がありました。全環境が同じ雛形から作られるので、新しく作られるレコードの ID が環境どうしで重なります。ID をキーにしているものが環境の外にあると、そこで上書きが起きます。たとえばオブジェクトストレージに置く添付ファイルや、共有している検索基盤の文書です。

アプリのコードは触らないと決めていたので、インデックス名や保存先を環境ごとに分ける改修はしません。代わりに、シーケンスの開始位置を環境ごとにずらしました。

```sql
-- 環境ごとの枠番号から開始値を決め、それより小さいシーケンスだけ進める
-- 何度流しても同じ結果になる（既に開始値以上なら触らない）
DO $$
DECLARE r record; cur bigint;
BEGIN
  FOR r IN SELECT c.oid::regclass::text AS seq
           FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
           WHERE c.relkind = 'S' AND n.nspname = 'public' LOOP
    EXECUTE format('SELECT last_value FROM %s', r.seq) INTO cur;
    IF cur < :base THEN PERFORM setval(r.seq, :base, false); END IF;
  END LOOP;
END $$;
```

`:base` は「雛形の開始値 + 枠番号 × 1環境あたりの幅」で決めます。枠の数と幅は、ID の型の上限に収まる範囲で決めます。

### フロントは仮のホスト名でビルドし、起動時に置き換える

フロントエンドは、API の URL をビルド時に文字列として埋め込みます。環境ごとにビルドし直すと1件あたり数分ずつ余計にかかるので、仮の値でビルドしたイメージを全環境で使い回します。

```sh
# nginx の起動前に実行する（/docker-entrypoint.d/ に置く）
sed -i -e "s|__PREVIEW_API_ORIGIN__|$PREVIEW_API_HOST|g" \
       -e "s|__PREVIEW_WEB_ORIGIN__|$PREVIEW_WEB_HOST|g" "$f"
# 置き換え後に仮の値が残っていたら、起動を止める
```

置き換えに失敗したまま起動すると、別の環境の API を呼ぶ画面が黙って出ます。ヘルスチェックでは気づけないので、仮の値が残っていたら起動させないようにしました。

### 自動で止めて、自動で消す

止め忘れは、仕組みで拾います。毎時と夜23時半に定期実行するジョブが、課題の状態と使われ方を見て、上から順に判定します。

1. 課題が「完了」→ 初めて見たときは24時間後を削除期限として記録し、期限を過ぎても完了のままなら削除する
2. 課題が「処理済み」で動いている → 停止
3. 夜の定期実行 → 停止（共有している DB クラスタが深夜に止まるため。固定指定した環境だけは通知のみ）
4. 10時間を超えて動き続けている → 停止
5. 稼働時間帯の外で、90分リクエストが無い → 停止

1つ目に猶予を置いたのは、課題の状態の付け間違いで消えないようにするためです。最後に、動いている環境が0ならロードバランサーも消します。

所要時間は、起動が約10分、前提データの投入が約2分、停止が約4分です。起動の大半は AWS の処理の完了待ちです。

### 証跡は Actions のランナーで撮る

画面の操作と撮影は、GitHub Actions のランナー上の Playwright で行い、画像は Artifacts で受け取ります。画像の解像度は、低すぎると2回指摘されたので 2880×1800 にしました。証跡をシートに貼る作業も道具にして、手で37枚を貼って約30分かかっていたものが、23枚で約3分になりました。

## ハマったところ

4つあります。どれも、動かすまで分かりませんでした。

### DNS の否定キャッシュ

動いている環境が0のときは、ロードバランサーもワイルドカードのレコードもありません。その間にホスト名を引くと NXDOMAIN が返り、ホストゾーンの SOA で決まる否定キャッシュの時間（ここでは900秒）だけ残ります。起動した直後に開けなくても、最大15分ほど待てば開けます。

### 長いホスト名で nginx が起動しない

課題番号を含めるとホスト名が長くなり、`server_names_hash_bucket_size` を広げないと nginx が起動しませんでした。手元の試験で先に見つかったのは幸運でした。

### CORS の許可元が設定ファイルに直書きされていた

検証環境の設定で、API の CORS の許可元が検証環境のホストに絞られていました。プレビューの画面から API を呼ぶと、プリフライトで弾かれます。アプリのコードを変えずに済ませるため、起動時に initializer を1つ差し込んで、許可元を環境のホストに置き換えました。

```ruby
# config/initializers/00_preview_overrides.rb（コンテナ起動時に置く）
# ファイル名を 00_ で始めるのは、CORS の設定より先に読ませるため（initializer は名前順）
Rails.application.config.web_url   = ENV.fetch("PREVIEW_WEB_URL")
Rails.application.config.admin_url = ENV.fetch("PREVIEW_ADMIN_URL")
```

通知メールに入るリンクの宛先も、同じ場所で置き換えています。

### クラウドのエージェントの通信経路が WebSocket を通さない

クラウドで動くエージェントは、プロキシ経由でしか外へ出られません。そのプロキシが WebSocket に対応しておらず、リアルタイム更新が届かない画面は確認できませんでした。撮影を GitHub Actions のランナーに移したのは、このためです。ランナーからは環境へ直接つながります。

## 捨てた案

| 案 | 採らなかった理由 |
|---|---|
| 1環境を直列のキューで使う | 案件ごとの前提データが次の案件に残る。消し漏れも名前で追えない |
| Draft PR のラベルで起動する | push のたびに多重に走る。抑える仕組みのほうが重くなる |
| インデックス名を環境ごとに書き換える | アプリのコードに手を入れることになる。ID の範囲をずらせば足りた |
| 検索基盤へテストデータを再投入する | 時間と費用に見合わない。確かめられないことの1つとして数えた |
| ワーカーを常駐させる | 試験が終わっても常駐させるのは費用の無駄。ジョブを流すたびに起動する |

どれも、作ること自体はできました。決め手は、試験が終わったあとに放っておけるかどうかです。

## 想定される反論

「ID の採番範囲をずらすだけで、環境どうしの汚染を本当に防げるのか」

防げるのは、ID をキーにした衝突だけです。すべてを防げるとは考えていません。

環境ごとに分かれているのは、DB とコンテナです。分かれていないのは、オブジェクトストレージと検索基盤です。このうち ID をキーにしているものは、範囲をずらすことで重ならなくなりました。ID 以外のキーで重なるものが残っていないとは、言い切れていません。

それでも、この形で始めました。環境ごとに完全に分けようとすると、アプリのコードに手を入れることになります。まずは構築基盤だけで回るかを確かめたかったので、テストに多少の制約がかかるのは、試す段階として許容しました。

「生成AIなどの外部サービスを止めた環境での確認を、STG テストと呼べるのか」

その部分については、呼べません。だから、この環境で確かめられなかった項目は、判定を「対象外（環境制約）」として残し、黙って OK にはしないことにしています。

対象外になった項目は、共有の検証環境で確かめます。実際に、外部の生成AIを使って処理が終わったときに届くメールの確認は、課題ごとの環境では止めていたので、共有の検証環境に戻して確かめました。

課題ごとの環境が受け持つのは、その案件の変更が、他の案件と混ざらない状態で動くかどうかです。外部サービスと組み合わせた確認まで、1つの環境に持たせようとはしていません。

「アプリのコードに手を入れない縛りは、かえって回り道ではないか」

回り道なのは認めます。CORS の許可元の差し替え、フロントの仮ホスト名の置き換え、シーケンスのずらし、と回避策をいくつも足しました。アプリを直せば、どれも1行で済んだかもしれません。

それでも縛りを外さなかったのは、確かめたかったことが「アプリに手を入れずに、構築基盤だけで回せるか」だったからです。プレビューのためのコードがアプリに入ると、本番で動くコードに、本番では使わない分岐が混ざります。回避策は構築基盤の側に閉じているので、要らなくなれば構築基盤ごと捨てられます。

「同時に動かせる環境の数に上限があるなら、結局は待ちが出るのでは」

上限を超えれば、待ちは出ます。上限の3は、実際に来ている開発依頼の案件数から、ひとまずのしきい値として決めました。

いまのところ、待ちは出ていません。待ちが出るようになったら、上限を上げるか、試験の終わった環境を早めに止める条件を足すかを考えます。

## まだ決めていないこと

クラウドで動くエージェントから workflow_dispatch で起動し、Artifacts を受け取る経路は、書いている時点でまだ実測していません。手元からは同じ REST API で通ることを確かめています。クラウドで通らなかったときに、どこで止まったのか（プロキシか、GitHub か）を切り分ける手順だけ先に用意しています。

もう1つは、Draft PR の作成をきっかけに自動で起動するかどうかです。ラベル起動を捨てたあと、いまはエージェントが課題キーで起動しています。PR を起点にした起動はまだ作っていません。1つの案件の変更が複数のリポジトリにまたがるので、どの PR を起点にするかが決まっていないためです。

## まとめ

- AI に設計から Draft PR まで任せると、次に詰まるのは検証環境だった。
- 「1環境を直列で使えば足りる」は、案件ごとの前提データがあるかぎり成り立たなかった。
- 単位をスタック1つにして、課題番号を名前に入れると、作るのも消すのも追いやすい。
- DB は TEMPLATE で複製し、シーケンスの開始位置を環境ごとにずらすと、アプリを触らずに ID の衝突を避けられる。
- タスクを止めてもロードバランサーの課金は止まらない。止めているつもりの環境ほど、何に課金されているかを確かめる。
