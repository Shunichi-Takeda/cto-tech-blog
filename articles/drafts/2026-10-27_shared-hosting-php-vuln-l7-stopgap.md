# パッチを当てられない側の脆弱性対応 — 共有サーバーのPHP重大脆弱性を、CDNの手前で止血した

2026年10月、PHPに認証不要で任意のコードを実行されうる重大な脆弱性が公表されました。

サービス本体とは別に、会社のサイトやサービス紹介のサイトをいくつか共有のレンタルサーバーで動かしています。管理画面でPHPのバージョンを選ぶだけで、php.ini も拡張モジュールも触れない種類のサーバーです。パッチを当てるのは事業者で、こちらは待つしかありません。

待つ間に手元で打てたのは、前段のCDN（Cloudflare）の設定だけでした。結論を先に書くと、止めるべきだったのは「問い合わせフォーム」ではなく「PHPに届く multipart の要求すべて」で、そのためにフォームの方が止まる、という順番でした。

![自分では直せないサーバーの手前で、攻撃の要求をCDNの盾で弾く流れと、フォームの入口だけ塞いでも別の入口から入られるが、サーバー全体の前で止めれば入らない、という見どころのドット絵](/images/shared-hosting-php-vuln-l7-stopgap/overview.png)

## 「うちは multipart を使っていない」は、安全の根拠にならなかった

最初に考えたのは「どのフォームが攻撃に使われうるか」です。報じられていた攻撃は、`multipart/form-data` のPOSTを入口にするものでした。そこでコードベースを検索し、multipart を送る書き方（`enctype`、ファイル選択欄、`FormData`、`$_FILES`）を洗い出しました。

使っていたのは、会社サイトの問い合わせフォームと、WordPressの管理画面での画像アップロードだけです。ほかのフォームはすべてURLエンコードのPOSTでした。

ただ、これは影響が無いことの根拠になりませんでした。PHPは、スクリプトを動かす前にPOSTの本文を解析します。報じられていた問題はこの解析の段階にあるので、アプリがアップロード機能を使っているかどうかは関係がありません。問題は「PHPにPOSTが届くURLがあるか」だけです。

検証環境で確かめました。POSTを処理しない静的なページ（拡張子は `.html`）に、空の項目を1つだけ持つ multipart のPOSTを1本送ります。

```bash
# 比較用の GET
curl -s -o /dev/null -D - https://stg.example.com/pricing.html | grep -i -E '^HTTP|x-powered-by'

# 空の項目1つだけの multipart の POST（本文は 152 バイト）
curl -s -o /dev/null -D - -X POST -F 'probe=' https://stg.example.com/pricing.html \
  | grep -i -E '^HTTP|x-powered-by'
```

どちらも `200` で、応答には `x-powered-by: PHP/8.x.xx` が付き、返ってきたページのバイト数も同じでした。CDNもサーバーも、このPOSTを止めていません。`.html` のURLもPHPを通る設定になっていたうえ、存在しないURLの404もPHPが返していました。PHPを通らないのは画像や `robots.txt` のような静的ファイルだけで、入口は事実上どのURLにもあったことになります。

## 手元に残っていたのは、CDNの設定画面だけだった

公表された緩和策には、PHPの設定を変える案もありました。しかしこのサーバーでは、管理画面に「php.ini の設定変更はできない」と明記されています。設定での緩和は選べませんでした。

サーバー側の `.htaccess` で multipart を弾く手もありますが、事業者は予防措置としてメンテナンスに入っていて、FTPも管理画面も順次止まっていました。置きたくても置けない時間帯です。

第三者が公開した、解析処理を差し替える拡張モジュールも見つかりました。ただ、拡張を読み込むには php.ini を書き換える必要があり、このサーバーでは使えません。作者自身もREADMEで、塞げるのは公式の修正の一部だけだと書いていて、公開されたのも当日でした。仮に使える環境でも、中身を確かめずに入れる選択は取らなかったと思います。

残ったのがCDNです。会社サイトはCloudflareを通していたので、PHPに届く前の層で止められます。

## フォームだけ止めても、止血にならない

当初はこう考えていました。問い合わせフォームを止め、PHPを上げるまでの1日だけ凌ぐ。

しかし前の節のとおり、攻撃はフォームの送信先でなくても、PHPが動くどのURLにでも送れます。フォームの送信先だけを塞いでも、ほかのURLから届きます。**止める単位を「サイト全体への multipart の要求」に変え、その結果としてフォームが送れなくなる**、という順番に直しました。遮断の条件そのものは、ここでは書きません。

止める前に確かめたのは、利用者からどう見えるかです。会社サイトの問い合わせフォームは、広く使われているフォームのプラグイン（Contact Form 7）で作られていました。配信中のスクリプトを読むと、送信が200番台以外で返ると、エラーをブラウザのコンソールに出すだけで、画面には何も表示しません。

つまり、遮断した状態で送信ボタンを押すと、スピナーが回り続けます。エラーも完了も出ず、利用者は「送れたのか分からない」まま離れていきます。こちらには問い合わせの記録すら残りません。

そこで順番を決めました。

1. 問い合わせページの本文を「一時停止中」のお知らせに差し替える（フォームは削除せず外すだけにして、戻しやすくする）
2. CDNで遮断する
3. 事業者の作業が明けたら、サーバー側でも遮断する（CDNを通らない経路には、CDNの遮断が効かないため）
4. PHPを修正版に上げたら、3→2→1の逆順で戻す

このうち3は、結果として入れられませんでした。理由は後の「想定される反論」で書きます。

お知らせの理由は「システムメンテナンス」に留め、脆弱性への対応だとは書いていません。

## 根拠を、報道から公式アドバイザリに付け直した

作業が一段落したところで、「multipart に影響がある、というのはどこの情報で、何を根拠にしたのか」と聞き返されました。

答えに詰まりました。公式の詳細は修正版の公開と同時に出る予定で、それまで手元にあったのは、セキュリティ企業のブログ、GitHubに置かれた第三者の資料、報道の又聞きです。「multipart が経路」は、それらとPHPの仕様を組み合わせた推定でした。最初は「報道ベース」と書き分けていたのに、やり取りを重ねるうちに言い切る表現に変わっていました。

ちょうどその頃、php.net の[公式アドバイザリ](https://www.php.net/archive/2026.php#2026-10-21-5)が出たので、根拠をそちらに付け直しました。読んで分かったことは2つあります。

- メモリを使い切らせる手口として挙げられていたのは、すべて multipart の解析の問題でした。緩和策としても「アプリが multipart を使わないなら、PHPに届く前のフロントで遮断する」と書かれています。CDNでの遮断は、公式が挙げる対策に当たりました。
- もう一方の脆弱性には、multipart と関係のない経路も確認されていました。遮断は経路を減らしますが、安全にはしません。公式の結論も、完全な対策は更新だけ、です。

CDNでの遮断は、更新までの時間を買う手段であって、更新の代わりにはなりません。

## 事業者のメンテナンス中は、エラーのときだけメンテナンス画面を出す

翌朝、事業者のメンテナンスで、サイトが502や500を返すようになりました。「トップに静的なページを置いて、メンテナンス中と出したい」という相談に対し、Cloudflareのカスタムエラールールを使いました。

```
条件:   http.response.code ge 500
応答:   HTMLレスポンス（メンテナンスページの中身をルールに直接書く）
コード: 503
```

トップに固定ページを置く方式と違い、オリジンがエラーを返したときだけ差し替わります。事業者の作業が明ければ、何もしなくても元のサイトに戻ります。戻し忘れも、復旧に気づかず止め続ける心配もありません。応答コードを503にしたのは、検索エンジンに「一時的」と伝えるためで、ページには `noindex` も付けました。

1つだけ、この条件で拾えないサイトがありました。記事を別のサーバーから読み込んで表示する作りのサイトで、読み込みに失敗すると、本文の無い404を返していました。

```js
// 記事が取れなかったときの返し方（修正前）
return new Response(null, { status: 404 });
```

このサイトには「特定のパスの配下で404なら」という条件も足しました。こちらは自動では戻らないので、復旧を確かめてから手で外す前提です。

この空の応答は、別の症状も起こしていました。「スマートフォンで記事を開くと document.txt がダウンロードされる」という報告です。本文が空で `Content-Type` も無い応答を、iPhoneのブラウザはページではなくファイルとして扱います。メンテナンスページのルールを入れた後は、同じURLが `text/html` の503になり、ダウンロードは止まりました。恒久対応として、エラー時もHTMLのエラーページを返すよう直しています。

## 外すときは、消さずに無効にする

事業者の作業が明け、修正の適用を確かめたサイトから順にルールを外しました。外すといっても削除はしておらず、すべて無効にしただけです。

残した理由は、次に同じ種類の事態が来たとき、有効に戻すだけで済むからです。条件式も、確かめた手順も、ルールの中に残ります。

## 想定される反論

「CDNでの遮断は根本対策ではない。更新を待つべきだったのでは」

そのとおりで、CDNでの遮断は根本対策ではありません。公式アドバイザリも、完全な対策は更新だけだと書いています。

ただ、このサーバーでは、更新を待つ以外の選択肢がもともとありませんでした。問題は、待つ間を何もせずに過ごすかどうかです。修正版がいつ提供されるかは事業者次第で、その夜は管理画面もFTPもメンテナンスで止まっていました。いつ明けるかも分かりません。手口が出回っている可能性が高い脆弱性を、終わりの見えない時間だけ開けたままにするより、手元の層で入口を絞る方を選びました。

外すことが前提の措置なので、入れる前に戻す順番まで決めておきました。実際に遮断していたのは、翌日の午後までの約16時間です。

「問い合わせフォームを止める業務影響を、止血のために許容してよいのか」

許容しました。比べたのは、問い合わせが半日ほど届かないことと、サイトを乗っ取られることです。後者には、ページの改ざんだけでなく、応募フォームで預かる書類の流出まで含まれます。前者は、お知らせを出しておけば、利用者が別の手段を取れます。

条件は、お知らせを先に出すことでした。黙って止めると、利用者は送れたのかどうか分からないまま離れていきます。こちらには、問い合わせがあったことすら残りません。

遮断していた間に止めた送信は十数件で、その一部は利用者の送信だった可能性があります。この点は割り切っています。

「CDNを通らない経路が残るなら、CDNでの遮断は意味が薄いのでは」

経路が残っていたのは事実です。サーバー側でも遮断する計画でしたが、事業者のメンテナンスが明けるより先にPHPの切り替えが済み、サーバー側の遮断は最後まで入れずに終わりました。

それでも、CDNで止めた意味はあったと考えています。公開しているホスト名に届く要求は、すべてCDNを通ります。CDNを通らない経路を使うには、まずその経路を知られる必要があります。穴をゼロにはできませんでしたが、誰でも叩ける入口は閉じられました。

## まだ決めていないこと

1つは、次の系列へいつ上げるかです。今回は修正版に上げて凌ぎましたが、どの系列もいずれサポート期限を迎えます。共有サーバーでは上げる時期を事業者の提供状況に合わせるしかなく、こちらの都合だけでは決められません。

もう1つは、無効にしたルールを、いつまで残すかです。残せば次回は速く動けます。一方で、使っていないルールが増えると、どれが生きているのか分かりにくくなります。

## まとめ

- PHPはスクリプトを動かす前にPOSTの本文を解析する。アプリが multipart を使っていないことは、影響が無い根拠にならない。
- パッチを当てられない環境では、CDNなど自分が持っている層で入口を絞る。ただしCDNを通らない経路には効かない。
- 止める単位は「フォーム」ではなく「入口となる要求」。止めた結果を利用者がどう見るかを先に確かめ、お知らせを先に出す。
- 根拠は公式アドバイザリに付け直す。推定のまま言い切った表現は、後から直す。
- メンテナンス表示は「エラーのときだけ差し替える」形にすると、復旧と同時に元へ戻る。
