# 毎朝のセキュリティ確認をAIに任せたら、判定の基準が「人が動く必要があるか」に変わった

本番環境に攻撃の兆候が来ていないかを、AIエージェントが平日の朝に確認して、判定付きのレポートを作るルーティンを動かしています。

動かし始めて1週間で、判定の基準を3回変えました。最初は「何かが起きたら赤」でしたが、それだと社員の普段の作業でも毎週赤になります。最後は、何が起きたかではなく、人が動く必要があるかで色を決める形に落ち着きました。

仕組みそのものより、この基準の変わり方の方が、同じことをやろうとしている人の役に立つと思います。

## ダッシュボードで足りるかを、先に棚卸しした

ルーティンを作る前に、既にあるダッシュボードとアラームで何が見えていて、何が見えていないかを一覧にしました。

結論は「見えていない範囲がある」でした。ダッシュボードはクエリを書いた攻撃しか拾えません。想定していない種類の攻撃は、そもそも画面に出てきません。アラームも、鳴った後に誰かが実行者や送信元を引きに行かなければ、何が起きたのかは分かりません。

足りない部分は、毎朝AIに取りに行かせることにしました。見るものは次の4系統です。

- 入口（WAF・ロードバランサー）の遮断数と、国別の通信量
- アプリケーションへのログイン失敗とロック
- クラウドのアカウントの乗っ取りの兆候（証跡の停止、権限の変更、外部への開放）
- 既存のアラームの状態遷移

このとき同時に決めたのが、ルーティンでは直さない、ということです。棚卸しの途中で、外に開いている設定の是正をAIが提案してきましたが、それは保留にしました。このセッションの目的はあくまで攻撃の状況把握で、是正は別の判断だからです。保留した事項は「既知の事項」として毎朝の確認に渡し、増えていないかだけを見させています。

## 構成は、読み取り専用の許可リストとスケジュール実行だけ

ルーティンの実体は、スケジュール実行されるエージェントへの指示書（プロンプト）1枚です。

```text
平日 9:35 に起動
  ├─ 観測窓: 前回の実行時刻から今回まで（月曜は金曜の実行から72時間）
  ├─ 許可リストにある読み取り専用のコマンドだけを実行
  │    cloudwatch get-metric-data / describe-alarm-history
  │    logs start-query / get-query-results
  │    cloudtrail lookup-events（呼び出しの間を空ける）
  │    ec2 describe-security-groups ほか
  ├─ 技術レポートをローカルに保存
  └─ 社内向けの共有ノートを1件作る（書き込みはこれだけ）
```

指示書の先頭に安全ガードを置き、許可リストに無い操作（作成・更新・削除・コンテナへの接続・DBへの接続・権限の変更）は実行せず、レポートの「要判断」に書くようにしています。書き込みの権限は、共有ノートの作成1件だけに使うキーを別に持たせました。

起動時刻は最初8:30にしていましたが、9:35に動かしました。手元のPCで動くスケジュール実行なので、PCが開いていない時間には走りません。監視の時刻を、監視する人の出社時刻に合わせることになったのは少し皮肉ですが、ここは割り切っています。

細かいところで2つ、最初から指示書に書いておいて良かったものがあります。

1つはタイムゾーンです。CLIの返すタイムスタンプはJSTで、Logs Insights の `@timestamp` はUTCです。AIはこの2つを平気で混ぜます。「レポートの時刻はJSTで書く」と明記しておかないと、深夜の出来事が朝の出来事として報告されます。

もう1つはスキャン量です。Logs Insights はスキャンした量で課金されるので、毎回 `statistics.bytesScanned` を合計してレポートに書かせ、1回の実行で上限を超えそうなら残りのクエリを止めて「未確認」にさせています。

## 固定の閾値をやめて、7日中央値と比べる

最初に捨てたのは固定の閾値です。

ログイン失敗が何件を超えたら異常、という決め方をすると、曜日やキャンペーンの有無で平常値そのものが動きます。そこで比較の基準を「同じ長さの窓の、直近7日分の中央値」に置きました。平均ではなく中央値にしたのは、1日だけ大きな攻撃があった週に、基準が引きずられて翌週の異常を見逃さないためです。

固定の閾値は補助に回しました。たとえば、証跡の停止は中央値と比べるまでもなく1件で赤です。

## 社員の作業でも鳴るので、毎週赤になった

運用を始めてすぐ、アカウントの変更を検知するアラームが、社員の通常の作業でも鳴ることが分かりました。権限の付け替えも、新しいバケットの作成も、正規の作業です。最初の基準ではこれが全部赤になり、毎週赤のレポートが出る状態になりました。

**毎週赤だと、誰も赤を読まなくなります。**

そこで、アラームが鳴ったら、該当するイベントの実行者・送信元・MFAの有無まで引かせ、全部が「社員のIAMユーザー」「社内の回線」「MFAあり」なら緑、それ以外が1件でもあれば赤、という形に変えました。証跡の停止のように、誰がやっても赤のままにするものは例外として列挙しています。

翌週、さらに一段緩めています。在宅や出張では社内の回線から外れるので、社外の回線からでも、社員の想定内の作業（リリース、調査のための読み取り、MFAありのコンソールログイン）は緑にしました。黄色にするのは、社外の回線からで、内容が想定外のもの（権限の変更、秘密情報の読み出し、外部への開放、実行者や目的が分からないもの）に限っています。

## 色の意味を「人が動く必要があるか」に揃えた

レポートは、技術職ではない社員も読む共有ノートとしても出しています。そうなると、色の意味が「何が起きたか」では伝わりません。遮断が急増した日に赤を出すと、読んだ人は「何か被害があったのか」と受け取ります。実際には防げているのに、です。

そこで判定を4段階と「未確認」に作り直しました。

| 色 | 意味 | 例 |
|---|---|---|
| 🔴 要対応 | すぐに人が動く | 証跡の停止、外部への新たな開放、社外からのMFAなしのログイン成功 |
| 🟡 要確認 | 人の確認・判断待ち。被害は未確認 | 社外の回線からの想定外の権限変更、届いてエラーが増えた原因不明の通信 |
| 🟢 対処済み | 何かあったが、防げている・説明がつく | 遮断の急増、社内回線での誤入力によるロック |
| 🔵 平常 | 何も起きていない | — |
| ⚪ 未確認 | 権限や仕組みの都合で見られていない | — |

基準を一言で言うと、**防げているもの、原因が分かっているものは黄色にしない**、です。

似た2つで差を書くと分かりやすいと思います。入口で遮断された通信が急増したなら、それは緑です。遮断できているからです。遮断されずにアプリまで届いて、エラーや失敗が増えていて、送信元か原因が分からないなら、それは黄色です。量は前者の方が多くても、人が動く必要があるのは後者だけです。

⚪は共有ノートには書かず、技術レポートにだけ残しています。技術職以外の人が「確認できていない」を読むと、確認できていないものの中身を想像して不安になるからです。

## 公開を「塞ぐ」操作で、公開のアラームが鳴った

基準を作り直している間に、外部への開放を検知するアラームが鳴りました。調べると、鳴らしたのはバケットの公開ブロックを有効にする操作、つまり公開を「塞ぐ」操作でした。社員が新しいバケットを作ったときの初期設定です。

仕組みは単純で、メトリクスフィルタがAPI名だけを数えていました。

```text
{ $.eventName = "PutBucketPublicAccessBlock" }
```

`PutBucketPublicAccessBlock` は、公開ブロックの4項目を true にする呼び出しにも false にする呼び出しにも使われます。API名だけを見ると、塞いだのか開けたのかが区別できません。バケットを新しく作るたびに鳴ります。

この種の監視を作るとほぼ必ず起きることなので、直し方の一般形を置いておきます。設定値が false のときだけ数え、ブロックそのものの削除は常に数えます。

```text
{ ($.eventName = "DeletePublicAccessBlock") ||
  ($.eventName = "DeleteBucketPublicAccessBlock") ||
  (($.eventName = "PutBucketPublicAccessBlock") &&
   (($.requestParameters.PublicAccessBlockConfiguration.BlockPublicAcls IS FALSE) ||
    ($.requestParameters.PublicAccessBlockConfiguration.IgnorePublicAcls IS FALSE) ||
    ($.requestParameters.PublicAccessBlockConfiguration.BlockPublicPolicy IS FALSE) ||
    ($.requestParameters.PublicAccessBlockConfiguration.RestrictPublicBuckets IS FALSE))) }
```

`requestParameters` の下の構造は、自分の環境で実際に記録されたイベントを1件取り出して確かめてください。フィールドのパスが1段ずれると、今度は何も数えない監視になります。鳴らない監視は鳴りすぎる監視より気づきにくいので、直した後に一度わざと false の設定を検証環境で入れて、鳴ることを見ておくのが安全です。

調べる側の教訓は1つです。外部への開放のアラームが鳴ったら、最初に「開けた操作か、塞いだ操作か」を見る。いまはこれを指示書の調べ方に入れています。

## AIが「ログが無い」と言い、それを前提に課題を起票した

もう1つ、AI側の誤りがありました。

WAFのログを調べる流れで、AIが「WAFのログが無い」と書き、それを前提に、ログを出す設定を足す課題まで起票しました。実際には、どちらの本番環境でも、ログは別の保存先に既に出力されていました。後で調べ直したAI自身が、課題の前提が誤りだったと訂正しています。

AIの「無い」は、AIが見た範囲に無かった、という意味でしかありません。この話は長くなるので、別の記事で扱います。

ただ、このときの調べ直しで判断材料が1つ増えました。WAFのログを全件ログの集約サービスに入れる場合と、遮断とカウントに絞ってストレージに直接出す場合とで、月額が2桁以上違いました。調べるときに必要な分だけあればよいので、後者にしています。

国で絞る案も出ましたが、採りませんでした。ログを国で絞るには、通信に国のラベルを付けるルールを足す必要があり、そのルールには評価するリクエスト数に応じた課金が全通信にかかります。調べるときにしか使わないログのために、平常時の全通信に費用を払うことになるので、割に合わないと判断しました。

## 想定される反論

「社外の回線からの操作でも緑にするのは、緩すぎるのでは」

（回答は著者が記入。答えるのに要る材料: 緑に倒した作業の範囲をどう決めたか、黄色に残したものとの境目、技術レポートには実行者と操作を全件残していること）

「本番環境の読み取りを、AIに毎朝渡してよいのか」

（回答は著者が記入。答えるのに要る材料: 許可リストで絞っている範囲、書き込みキーを分けた理由、読み取りでも漏れうる情報をレポートに書かせないルール）

「アラームとダッシュボードを足せば、AIは要らないのでは」

（回答は著者が記入。答えるのに要る材料: アラームは鳴った後に誰かが実行者や送信元を引く必要があること、その引く作業をAIに渡した効果、クエリを書いていない攻撃は拾えないこと）

「手元のPCで動くルーティンを、監視と呼べるのか」

（回答は著者が記入。答えるのに要る材料: PCが閉じている日の扱い、これはリアルタイムのアラームを置き換えるものではなく補うものだという位置づけ）

## まだ決めていないこと

共有ノートの投稿は、これまで下書きを人が承認してから出していました。これを自動投稿に切り替えます。ただし総合判定が赤の日だけは承認制に戻します。誤報で社内を騒がせることの方が、1時間遅れることより害が大きいと考えているからです。この線引きで足りるかは、自動投稿で何週か回してから見直すつもりです。

もう1つは、ルーティンを手元のPCから外に出すかどうかです。今は「PCが開いていれば動く」という前提に乗っています。クラウドで動かせばこの前提は消えますが、本番の読み取り権限をどこに置くかという別の問題が出てきます。どちらを取るかは、まだ決めていません。

## まとめ

- 固定の閾値ではなく、同じ長さの窓の7日中央値と比べる。固定の閾値は、1件で赤にするものだけに使う。
- 判定の色は「何が起きたか」ではなく「人が動く必要があるか」で決める。防げているもの、原因が分かっているものは黄色にしない。
- 技術職以外も読むなら、確認できていないことは共有の場に書かず、技術レポートにだけ残す。
- API名だけを数えるメトリクスフィルタは、塞ぐ操作でも鳴る。設定値まで見る形にし、直した後に鳴ることを確かめる。
- AIの指示書には、タイムゾーンとスキャン量の扱いを最初から書いておく。
