# LLMにもEOLがある — モデルを依存ライブラリとして管理する

LLMを本番に組み込むとき、私が最初に見落としていたのは「そのモデルはいつまで使えるのか」でした。

Railsのバージョンなら誰でもEOLを気にします。PostgreSQLなら次のメジャーアップグレードを計画に入れます。ところがモデルについては、選定時の議論は精度とコストばかりで、寿命の話が出てこない。少なくとも私は出していませんでした。

## モデルには提供終了がある

気づいたきっかけは、まったく別の作業でした。コスト最適化のために利用モデルの一覧を眺めていて、EOLの列に目が止まった。日付が過去になっている。何をどう見ても終わっているとしか見えない。**椅子からずっこけました。**

Amazon Bedrockには[モデルライフサイクル](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html)というドキュメントがあり、各モデルは `Active` → `Legacy` → `EOL` と遷移します。`Legacy` になった時点で提供終了日が示され、EOLを過ぎると呼び出せません。Bedrockに限らず、主要プロバイダはどこも同じ構造です。モデルは永続的なインフラではなく、期限付きの依存物です。

厄介なのは、EOLが近づいてもアプリケーションは何も言わないことです。gemの脆弱性なら `bundle audit` が教えてくれるし、EOLの近いランタイムならCIが警告を出す。モデルにはそれがありません。ドキュメントを能動的に見に行った人だけが知っている状態になります。

## 差し替えで壊れるのはコードではない

「モデルIDを1行変えるだけ」——移行前の私の見積もりはこれでした。変える行数はその通りです。

問題はその先で、同じプロンプトに対して挙動が変わります。

いちばん厄介だったのが回答拒否です。新しいモデルは安全側に寄っていて、以前なら普通に処理していた入力に対して、答えられるのに答えないという返し方をしてきます。「確実に返してください」と強く指示すると、今度は「不安なので、やめておきます」と言ってくる。悪意はなく、慎重なだけです。ただ、こちらは慎重さを求めていません。

数十件のバックテストで分かったのは、そのままのプロンプトでは1割程度が「回答できないケース」として返ってくることでした。どこまで踏み込んで返してよいかの線を、プロンプト側で引き直す必要がありました。

他に変わるのは、口調と冗長さ（UIに直接載せていると体験の印象が変わる）、そしてJSONなど出力形式指示への従順さです。

つまり**移行作業の本体はプロンプトです**。ここを見積もりに入れていないと、リリース直前に「動くけれど品質が違う」に気づいて慌てます。私は慌てました。

そして回答拒否がとくに危ないのは、エラーにならないことです。200が返り、それらしい日本語が入っている。監視は全部正常を示します。 気づけるのは、ステージングで実際の業務入力を通した人間だけです。

## 移行時に一緒に片付けられること

差し替えは周辺構成を見直す好機でもあります。検討したのは推論プロファイルでした。

Bedrockの[cross-Region inference](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)は、リクエストを複数リージョンに振り分けます。日本向けのプロファイルなら東京と大阪が対象です。

```bash
aws bedrock list-inference-profiles --region ap-northeast-1 \
  --query 'inferenceProfileSummaries[].{name:inferenceProfileName,id:inferenceProfileId}' \
  --output table
```

呼び出しでは、モデルIDの代わりにプロファイルのIDまたはARNを渡します。

```ruby
# Ruby (aws-sdk-bedrockruntime)
client = Aws::BedrockRuntime::Client.new(region: "ap-northeast-1")
client.converse(
  model_id: ENV.fetch("BEDROCK_INFERENCE_PROFILE_ID"),
  messages: [{ role: "user", content: [{ text: prompt }] }]
)
```

効くのはスロットリング耐性です。単一リージョンのクォータに張り付いていた処理が、振り分けで通るようになります。ただしデータが別リージョンを経由するため、データ所在の要件がある場合は対象リージョンの確認が要ります。ここは技術判断ではなく契約・コンプライアンスの判断なので、私は勝手に決めずに確認を挟むことにしています。

なお、モデルIDを環境変数に出しておくと次回の移行コストが下がります。上のコードのように外から差し替えられれば、「どこにモデルIDが埋まっているか探す」工程は消える。地味ですが、EOLは繰り返し来るので効きます。

## 運用に組み込んだこと

モデルのEOLを開発計画のマイルストーンに載せる。 これが一番効きます。EOL日を、リリース計画やDBのバージョンアップと同じ扱いでスケジュールに置く。そうすると「EOL2ヶ月前に移行検証を始める」という逆算が働きます。ドキュメントを定期的に見に行くという運用は、忙しい時期に必ず飛ぶので信用していません。

完了条件を「動く」ではなく「品質が同等」にする。 実際の業務入力を通した比較確認をステージングで行い、回答拒否とトーンを見る。ここを飛ばすと監視をすり抜けます。

移行を1つのモデルで終わらせない。 用途ごとに複数使っている場合、EOLは別々に来ます。並べておかないと、片方を終えた達成感でもう片方を忘れます。

## 想定される反論

「抽象化レイヤーを噛ませてプロバイダ非依存にすれば済むのでは」

抽象化レイヤーは既にあります。モデルIDの差し替えそのものは設定変更で終わります。それでもこの記事を書いているのは、差し替えた後に残る作業のほうが本体だからです。

コードの依存は抽象化で切れます。切れないのは、そのモデルの癖に合わせて書いたプロンプトのほうです。

「EOLまで猶予があるのに、大げさでは」

猶予が長いことが、そのまま油断になります。期限までの間もアプリケーションは正常に動き続けるので、放置しても何も起きません。

そして期間が長いほど、組み込んだ本人が現場にいない可能性が上がります。リマインドを仕込んでも、なぜその設定になっているかを知らない人が受け取ることになる。猶予は準備のための時間であると同時に、経緯が失われていく時間でもあります。

「プロンプトの再評価は自動化できるのでは」

できます。バックテストは半自動で回していて、評価スコアも算出しています。

問題は使う頻度です。モデルの入れ替えはおそらく1〜2年に1回で、その頻度でしか動かさない仕組みは浮きます。次に使うときには前提が変わっていて、整備し直すところから始まる。自動化そのものより、必要になったときに動く状態で保てるかのほうが難しいと思っています。

「モデル更新は精度が上がるのだから、むしろ歓迎では」

上がることはあります。ただ、精度の尺度は最終的に利用者がどう感じるかに寄ります。機械的なスコアはある程度見えますが、その出力が利用者にとって有益かどうかは別の話です。常に最新を追えばいい、とはなりません。ビジネス面でのコストも見る必要があります。

だからこそ、更新を歓迎するかどうかとは切り離して、期限は期限として計画に載せる必要があります。

## まだ決めていないこと

自動化の余地はあります。モデルの状態を定期取得して、`Legacy` に落ちたら通知する。技術的には難しくありません。

ただ、通知を作っても移行そのものは自動化できません。プロンプト再チューニングが本体だからです。通知を増やして安心し、実作業の見積もりが甘いままになるほうが危ないのではないか、という気もしていて、まだ手をつけていません。

## まとめ

- LLMには提供終了がある。永続インフラではなく期限付きの依存物として管理する。
- EOLはアプリケーションから観測できない。ライフサイクル情報を能動的に取り、開発計画のマイルストーンに載せる。
- 移行の本体はコード変更ではなくプロンプトの再チューニングと再評価。回答拒否の変化は監視をすり抜けるので、業務入力での比較確認が要る。
- モデルIDは環境変数に出す。EOLは繰り返し来る。
