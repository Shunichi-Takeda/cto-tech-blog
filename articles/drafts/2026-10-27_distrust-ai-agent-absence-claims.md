# 「ありません」と言い切るAIを疑う — エージェントの“不在の断定”が外れた5つの場面

AIエージェントに調査を任せていて、一番外れやすいのは「無い」という報告です。

「有る」は、その1件を見せれば済みます。「無い」は、調べた範囲の外については何も保証しません。それなのに、エージェントの報告では「有る」と「無い」が同じ確からしさの文で返ってきます。

ここ2か月の作業で、エージェントが「無い」と言い切って外れた場面が5件ありました。並べてみると、外れ方は4種類に分かれます。対策の要は、**「無い」と言うときは、どこを見て無いと言ったのかを必ず添えさせる**ことだと考えています。

![照らした箱だけを見て無いと言うが、照らしていない箱にはある流れと、「無い」だけでなく見た所と見ていない所を書く、という見どころのドット絵](/images/distrust-ai-agent-absence-claims/overview.png)

## 外れた5件

### 「このフレームにコメントは付いていませんでした」

デザインツールの画面に付いたレビューコメントを読ませたときです。エージェントはブラウザでデザインファイルを開き、こう報告してきました。

「このフレームにコメントは付いていませんでした」

こちらから「ブラウザ拡張からなら、コメントも読めるのでは」と返したところ、15件ありました。

原因は、コメントパネルの絞り込みです。パネルは既定でファイル全体のコメントを新しい順に出すので、他のページのコメントで埋まり、対象のページのものが1件も見えていませんでした。「現在のページのみ」の絞り込みを有効にした瞬間に全件出ています。

もう1つ、エージェントはコメントのピンを探して、他の人のカーソル（共同編集で表示される丸いアバター）をピンと取り違えていました。「ピンが見当たらない」も、無いことの根拠になっていなかったわけです。

### 「制限が存在しない」

限定公開している機能が、対象外の利用者からも使えてしまわないかを調べさせたときです。エージェントはバックエンドのコードを読み、こう結論しました。

「公開範囲の制限は存在しません」

こちらから「その制限は今フロントエンド側に入っているはずです」と返すと、すぐに訂正が来ました。フロントエンドには3重のゲートがあり、メニューが描画されないうえに、URLを直接打っても元の画面に戻される作りになっていました。バックエンドだけを見て結論を出したのが原因です。

同じ調査の中で、エージェントは別の「無い」も報告しています。機能を有効にするための設定のレコードが、データベースに1件も無い、というものです。こちらは正しかった。データベースを直接引いて、0件を見ていたからです。

同じ調査の、同じ「無い」でも、正本を見て言った「無い」は当たり、一部だけを見て言った「無い」は外れています。

### 「Applied patch cleanly.」

これは「無い」とは逆向きに見えますが、構造は同じです。

別ブランチの変更を、パッチにして今のブランチへ当てさせたときです。ツールはこう出力しました。

```text
$ git apply --3way change.patch
Applied patch to 'presenter.tsx' cleanly.
```

エージェントは念のため、適用後の行数を元のブランチと比べました。ファイルは適用前と同じ431行のままで、何も削除されていませんでした。3-way の判定が、相手側に入っていた修正を「同等の変更が既に入っている」と見なして、何もしなかったように見えます。ただ、なぜそう判定したのかまでは突き止めていません。

ツールの「成功した」は、ツールがエラーを出さなかったという意味です。変更が入ったという意味ではありません。エージェント自身もこのとき「ツールの成功報告は結果の確認にならない」と書いています。

確かめ方は単純で、差分が本当に出たかを見るだけです。

```bash
git apply --3way change.patch
# 適用後、狙ったファイルに差分が出ているかを見る。空なら何も当たっていない
git diff --stat -- path/to/presenter.tsx
# 期待した変更の量と合っているかを、行数でも突き合わせる
wc -l path/to/presenter.tsx
```

### 「このサービスは休眠中です」

コンテナのベースイメージを棚卸しさせたときです。エージェントは各サービスのリポジトリの最終コミット日を見て、更新が止まっているいくつかを「休眠中」と判定しました。

次の段階で実際のコンテナの稼働数を引いたところ、そのうちの複数が本番で動いていました。コードの更新が止まっていることと、サービスが止まっていることは別です。むしろ、コードが更新されていないのに本番で動き続けているものこそ、古いイメージのまま残りやすい対象でした。

### 「WAFのログが無い」

セキュリティの確認の流れで、エージェントが「WAFのログが無い」と書き、それを前提に、ログを出す設定を足す課題まで起票しました。実際には、ログは別の保存先に既に出力されていました。エージェントが見たのは、ログの集約先だけでした。

この件は、後で調べ直したエージェント自身が訂正しています。ただ、課題は「無い」を前提に書かれた状態で、一度出てしまっていました。

## 外れ方は4種類だった

5件を並べると、外れ方は次の4種類に分かれます。

| 外れ方 | 該当 | 何が起きたか |
|---|---|---|
| 見た範囲が狭い | コメント、制限 | 一部のページ・一部の層だけを見て、全体として「無い」と言った |
| 道具の報告を結果と見なした | パッチ | エラーが出なかったことを、変更が入ったことと取り違えた |
| 代理の指標で判断した | 休眠 | コミット日という代わりの指標で、稼働しているかを判断した |
| 置き場所の前提を取り違えた | ログ | 自分の想定する場所に無いことを、存在しないことと取り違えた |

共通しているのは、どれも「見た場所には確かに無かった」ことです。エージェントは嘘をついていません。見た場所の外について、黙って一般化しているだけです。

見つけたきっかけも書いておきます。5件のうち2件はこちらからの問い返しで、3件はエージェント自身が次の手順で事実を確かめて気づいています。後者の3件は、行数を比べる、稼働数を引く、設定を読み直す、という一手を打っていました。気づけるかどうかは、その一手を打つかどうかで決まっていました。

## 「どこを見て無いと言ったか」を添えさせる

エージェントに渡す共通の指示には、次の形の決まりを置くのが効くと考えています。

```text
「無い」「0件」「存在しない」「該当なし」と報告するときは、必ず次の3つを添える。

1. 見た場所: どのファイル・どの層・どの画面・どのクエリで確かめたか
2. 見ていない場所: 同じものが在りうるのに、今回は見ていない場所
3. 正本かどうか: 見た場所が、その事実の正本（データベース、実際の稼働状態など）か、
   代わりの指標（コミット日、ドキュメント、命名）か

道具が「成功した」と返したときは、変更が実際に入ったかを差分か行数で確かめてから報告する。
```

見ていない場所を書かせるのが要点です。「バックエンドを見て制限は無かった。フロントエンドは見ていない」と書かれていれば、読んだ側が一瞬で気づけます。問い返しで見つかった2件は、どちらもこれが書かれていれば、問い返す前に気づけたはずです。

個別の手順には、外れたときの対処を既に書き足しています。コメントを読む手順では「現在のページのみ」の絞り込みを必須の手順に上げ、「ピンが見当たらない」は根拠にならないと明記しました。

採らなかった案もあります。エージェントに「無い」と言わせないようにする、つまり「見つからなかった」としか言えないように縛る案です。これは採りませんでした。設定のレコードの件のように、正本を見て言った「無い」は正しく、判断の材料として一番強いものです。言い方を縛ると、正しい「無い」まで弱くなります。縛るべきなのは言い方ではなく、根拠の添え方だと考えました。

## 想定される反論

「結局、人が全部確かめ直すなら、エージェントに任せる意味が無いのでは」

確かめ直すのは「無い」の報告だけです。「有る」は、その1件を見れば済みます。

それに、確かめ直すのは人とは限りません。5件のうち3件は、エージェント自身が次の一手（行数を比べる、稼働数を引く、設定を読み直す）を打って気づいています。見ていない場所が書いてあれば、人がやるのは「そこも見て」と返すことだけです。調べ直す作業そのものは、またエージェントに任せられます。

「見ていない場所を書かせても、エージェントは見ていない場所を知らないのでは」

半分はそのとおりです。

書けるのは、在ることを知っていて見なかった場所です。制限の件では、エージェントはバックエンドを読んだことを分かっていました。書かせれば「フロントエンドは見ていない」とは書けたはずです。

書けないのは、在ることを知らない場所です。ログの件では、エージェントは別の保存先があることを知りませんでした。知らない場所は、見ていない場所として挙げようがありません。

そこを埋めるには、エージェントの側ではなく、渡す側が正本の置き場所を教えるしかありません。「まだ決めていないこと」に書いた、正本の一覧を渡す案がそれです。

「同じことは人間の調査でも起きる。AI特有の問題ではないのでは」

起きること自体は、人間も同じです。違うのは、報告の見え方です。

人間は、自信の無い「無い」を、言い淀んだり「見た限りでは」と付けたりして伝えます。エージェントは、確かめ切った「無い」も一部だけ見た「無い」も、同じ調子で言い切ります。そのうえ、報告が短い時間にまとめて返ってくるので、読む側が1件ずつ確からしさを見分けにくい。

外れ方は人間と同じでも、外れていることに気づく手がかりが文面に出てこない。そこがエージェント特有だと考えています。

## まだ決めていないこと

3つの添え書きが、どれだけ効くかはまだ測っていません。入れた後で「無い」が外れた件数を数えるつもりですが、そもそも外れたことに気づかなかった件は数えようがありません。気づけなかった件をどう拾うかは、まだ手が無い状態です。

もう1つは、正本かどうかの判断をエージェントに任せてよいかです。コミット日を正本だと思い込んだのはエージェント自身なので、「正本かどうか」を書かせても、同じ思い込みのまま「正本です」と書いてくる可能性があります。ここは、よく使う事実について正本の置き場所を一覧にして渡す方が確実かもしれません。どちらにするかは、もう少し件数を見てから決めます。

## まとめ

- エージェントの「無い」は、見た範囲に無かったという意味でしかない。「有る」と同じ確からしさで受け取らない。
- 外れ方は、見た範囲が狭い、道具の報告を結果と見なす、代理の指標で判断する、置き場所の前提を取り違える、の4種類だった。
- 「無い」と報告させるときは、見た場所・見ていない場所・正本かどうかの3つを添えさせる。
- 道具の「成功した」は、差分か行数で確かめるまで結果ではない。
